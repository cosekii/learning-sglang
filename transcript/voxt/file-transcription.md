## Prose · Where this chapter's claims come from

Step 1 reads the two routes. `runTranscribeCLI` hands the command to `transcribeCLI` with a socket under the app's data folder (`Voxt/transcribe_cli.go:35-39`). The app's `fileRecognizer` uses the speech model set for Transcribe (`Voxt/transcribe_socket.go:58-88`) and calls `asr.Recognize` directly, so no dictation session runs, no cleanup runs, and no history row is written. Dictation itself writes history only when `Privacy.KeepHistory` is enabled, which is the default (`Voxt/internal/session/run.go:572-576`, `Voxt/internal/settings/settings.go:373-380`). `Voxt/docs/transcribe.md` describes the command as a separate route.

Step 2 reads decoding. `decodeAudio` checks the file, makes a temporary folder, runs macOS `afconvert -f WAVE -d LEI16@16000 -c 1`, reads the WAV, and returns PCM (`transcribe_cli.go:111-139`). `asr.SampleRate` is 16000 (`Voxt/internal/asr/asr.go:32`). The stage's 8-second example is constructed: $8 \times 16{,}000 \times 2 = 256{,}000$ PCM bytes, plus the 44-byte WAV header.

Step 3 reads the handoff. The socket is `transcribe.sock` in the app's data folder (`Voxt/internal/fileasr/socket.go:16-17`); `historyapi.Listen` binds it and sets mode `0600` (`Voxt/internal/historyapi/server.go:101-114`). The request is one JSON line with `op`, `bytes` and an optional `lang`, followed by the PCM (`socket.go:35-39`). `Lang` carries `json:"lang,omitempty"` (`socket.go:38`), and `Transcribe` marshals the struct directly (`socket.go:146`), so without `--lang` the key is omitted; after Unmarshal it is `""`. The server answers one reply line per segment and then a `done` line with the count (`socket.go:41-46`). The command writes the PCM while it reads replies, and `fileasr.Run` cuts and recognizes as the stream arrives (`socket.go:168-176`, `fileasr.go:39-74`). The request-line cap is 4 KiB (`socket.go:25-29`).

Step 4 reads the end of a cue. `Cutter` works in 10 ms slices at 16 kHz (`Voxt/internal/meeting/cutter.go:9-19`). It ends a cue after 450 ms of quiet (`cutter.go:70-74`).

Step 5 reads the start and the minimum. `startUtterance` starts a cue 300 ms before its speech (`cutter.go:95-105`). On the pause path, `finalize(end, true)` drops a cue with less than 350 ms of voiced sound (`cutter.go:119-127`); at EOF, `fileasr.Run` calls `c.Flush()` (`fileasr.go:67-68`), which emits the remaining cue without that check (`cutter.go:84-92`).

Step 6 reads the length cap. When a cue reaches 7 s without a 450 ms pause, `cutAtQuietest` searches the last second and cuts at the midpoint of the quietest 100 ms window (`cutter.go:75-78`, `cutter.go:130-147`, `cutter.go:189-199`). The rest of the buffer continues as the next cue.

Step 7 reads recognition. `fileasr.Run` cuts the stream and calls the recognizer once per cue, in order, dropping a cue whose trimmed text is empty (`Voxt/internal/fileasr/fileasr.go:39-74`). `fileRecognizer` uses the model chosen for Transcribe and uses the command's `--lang`, or dictation's language hint when it is empty (`transcribe_socket.go:58-88`). A missing `--lang` is left out of the wire (`omitempty`) and reaches the app as `lang:""` (`socket.go:35-39`).

Step 8 reads the output format. `Write` emits SRT as a number, `HH:MM:SS,mmm --> HH:MM:SS,mmm` and the text, or text as one line per cue (`fileasr.go:76-104`). Without `-o`, or with `-o -`, it writes to stdout.

Step 9 reads the write timing. A recognition error returns before the command opens the output, so it creates or overwrites no file (`transcribe_cli.go:73-87`). After recognition succeeds, the command calls non-atomic `os.WriteFile`; a disk-write failure can truncate an old file or leave a partial new file (`transcribe_cli.go:91-100`).

Step 10 reads what is kept. Dictation writes history only when `Privacy.KeepHistory` is enabled, which is the default (`Voxt/internal/session/run.go:572-576`, `Voxt/internal/settings/settings.go:373-380`). The app's completion hook writes only `transcribed a file for the command line: <length> of audio, <count> segments`, never the text (`transcribe_socket.go:90-98`).

Step 11 reads where the audio goes. `fileRecognizer` chooses Transcribe's model (`transcribe_socket.go:64-80`), and `docs/transcribe.md` says the audio goes to that on-device model or the remote service set for Transcribe, with no history entry and no recording. The chapter's last line asks how model files reach the Mac, which is the next chapter.
