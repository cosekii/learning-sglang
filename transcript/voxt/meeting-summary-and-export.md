## Prose · Where this chapter's claims come from

Step 1 reads the chain. When the final pass finishes and the auto-summary switch is on, `runFinalize` starts `correctAndSummarize` in the background: correction first, summary second (`Voxt/internal/meeting/manager_finalize.go:53-99`). A correction that fails only logs a warning; the summary still runs on the text as recognised (`manager_finalize.go:121-133`). The switch is `NoAutoSummary` (`Voxt/internal/settings/meeting.go:14`); correction and summary can also be re-run by hand (`Voxt/meeting_link.go:247`, `Voxt/meetings_detail_controller.go:214`). Not drawn: the speculative overlap that corrects the first track while the second still transcribes (`manager_finalize.go:63-75`, `correct_overlap.go`); its finished batches are reused by the correction, which changes no outcome this chapter shows.

Step 2 reads the batching. One correction request carries at most 250 lines and 20,000 runes of text (`correct.go:31-34`), as a JSON array of `{"i", "text"}` pairs; the system prompt adds the speech context, the matching dictionary terms and the dictionary notes (`correct.go:138-158`). A line the answer leaves out or empties stays as recognised, a batch whose request fails keeps its lines, and every other batch lands in one atomic save; times, speakers and order are untouched (`correct.go:60-105`). An answer that does not parse corrects nothing (`correct.go:160-183`). The batch rune count on the stage, 106, counts the five lines' text only, as the code does.

Step 3 reads the re-read. The summary loads the meeting from the store after correction, so it sees the corrected text when correction landed and the recognised text when it failed (`manager_summary.go:23-31`). The record is `Speaker：text` lines (`summary.go:111-125`; Me is the user, s1 is Speaker 1, `summary.go:96-109`). Long transcripts are summarised in 12,000-rune windows, each answer trimmed to 4,000 runes and summarised again until one remains (`summary.go:15-17`, `GenerateSummary`). The answer is one JSON object — title, content, todo_list — and the title and summary are written on the meeting row (`summary.go:20-90`, `manager_summary.go:55-66`). The summary is written in the user's main language, or the transcript's majority language when that is unset (`manager_summary.go:84-92`, `summary.go:148-152`). The stage's 145 runes are the five record lines plus their newlines; the long-call chain 100,000 → 9 → 9 → 3 → 1 is constructed: 100,000 runes make ⌈100,000 / 12,000⌉ = 9 windows, nine ≤4,000-rune answers regroup into 3, and three more into 1.

Step 4 reads the window picking. A follow-up question takes the whole transcript when it fits — three windows and 6,000 runes — else scores each 6,000-rune window by how often the question's words appear in it and keeps the top three within the budget (`followup.go:11-14`, `RelevantFollowUpContext`, `followup.go:67-105`). A whole-meeting question ("overall", "总结", …) takes the first and last window instead (`followup.go:214-226`). The stage counts only the deciding words; the code counts every word of two letters or more plus CJK bigrams (`followup.go:184-212`). The prompt names the transcript the primary source, the summary and chat only compressed context (`followup.go:22-38`), and the question and answer are appended to the meeting's stored chat (`manager_followup.go:38-63`). The stage's window 12 is constructed: in a 100,000-rune call there are ⌈100,000 / 6,000⌉ = 17 windows, and one 6,000-rune window fills the budget alone.

Step 5 reads the two buttons. Copy writes the plain-text export to the clipboard; Save… runs a file dialog and writes a `.txt` or `.md` named from the meeting's title (`meetings_detail_controller.go:246-289`). A text line is `mm:ss Name text`, a Markdown line `**mm:ss** Name text` under `# title`, and a translated line rides as `-> ` or `> ` (`export.go:17-77`). Labels come from the stored speaker: `me` is Me, `s1` is Speaker 1 or the name the user gave it (`summary.go:96-109`).

Step 6 is the map back. Correct reads the stored lines and the dictionary and rewrites words only; summarize reads the stored transcript, corrected or not, and writes the title, summary and to-dos; ask reads picked windows, the summary and the earlier chat and appends the answer; export reads the stored lines and writes the clipboard or a file. Which of these claims carry code tests, sample evaluations or real-device checks — and what stays unproven — is Chapter 16.
