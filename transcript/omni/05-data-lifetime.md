## Prose · Where this chapter's claims come from

Step 1 constructs two results, A and B, with one illustrative storage space. `talker_ar` is still reading A when B becomes available. Reusing the space immediately would replace A before its reader finishes; keeping A readable makes B wait. The one-space pool is a teaching device, not a configured SGLang-Omni limit. This step covers safe reuse, not a particular transport, allocation algorithm or performance claim.

Step 2 constructs a version-1 DataRef for object A using SHM. Its `object_id`, `transport` and `buffer` identify the object, select a relay and carry backend read information. The tensor bytes remain in the backend. DataRef contains neither a reader count nor ACK state; fan-out uses separate per-target lifecycles. The figure omits the other reconstruction fields and the direct same-process and PyTorch CUDA IPC bypasses.

Step 3 follows the generic relay path. The payload write returns a DataRef and a live `RelayOperation`. Before sending DataReady, the sender registers `PendingTransfer` under the DataRef's `object_id`; that record owns the operations and ACK future. The watcher starts after the control message is sent, and only then does the worker complete `job.ready`. Thus `send_payload()` reports write and publication completion, not receiver consumption or application completion.

Step 4 uses the generic receive path. The receiver deserializes DataRef, selects its transport's relay, allocates `buffer.length` bytes, performs and waits for `get_async`, then reconstructs tensors and the payload. A successful ACK is sent before the input handler receives the payload. The ACK reports data-plane read completion, not downstream computation. Failed reads use `success=False`; request-level `relay.cleanup` is not a universal sender-data release operation.

Step 5 follows the normal sender completion path. `ack_transfer` matches `ack.object_id` to pending and completes or fails its ACK future; a stale ACK is ignored. On success, `watch_pending` calls `mark_receiver_done` and awaits completion for every operation, then removes pending and releases an optional KV lease. Backend resource reclamation belongs to each concrete `RelayOperation`; the generic interface has no universal `release()` and some failure paths intentionally retain pending.
