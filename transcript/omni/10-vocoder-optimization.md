## Prose · Where this chapter's claims come from

Step 1 follows Qwen3-Omni's default streaming Code2Wav windows in `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:79-109,999-1011`. A later stateless window reads 25 earlier frames and 10 new frames, then emits only the 10 new frames. Learning SGLang Ch. 20 Steps 1–3 established that those 10 frames represent 800 ms of playback. The three map entries are cross-request batching, retained codec state and exact-shape CUDA graphs; later steps explain each one. The frame counts describe input work, not elapsed time.

Step 2 follows `sglang_omni/scheduling/streaming_vocoder.py:819-842` and `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:999-1079`. The constructed comparison changes three independent `[B=1,T=10]` first-window calls into one `[B=3,T=10]` call. Real groups also require matching first/later kind and whether each request uses saved decoder work. They contain at most eight replay rows and do not pad unlike lengths into one replay. `tests/unit_test/qwen3_omni/test_code2wav_batching.py:111-191` checks shared rows and the first/later boundary. The 3→1 count is not a timing result.

Step 3 follows `sglang_omni/models/qwen3_omni/components/codec_state_pool.py:13-24,63-115` and `code2wav_scheduler.py:296-327,999-1011,1283-1300`. A slot holds earlier attention K/V and convolution buffers that join windows; their ring and overlap layouts are deliberately not covered. The first window writes state; a later slot-backed window reads only 10 new frames instead of 25 old plus 10 new. A request without a free slot remains stateless for life, and a short stream ending before its first threshold window decodes statelessly. The 35→10 comparison counts input frames, not latency or memory savings.

Step 4 quotes [public PR #2909](https://github.com/sgl-project/sglang-omni/pull/2909), measured on Qwen3-Omni colocated BF16 on H200 with eight rows and one graph replay, median of 20 timings. The first window rises from 3,656.3 to 3,992.0 µs because it writes state; the later window falls from 10,777.5 to 4,255.3 µs. Both arms use graph replay, so this is a retained-state comparison, not a graph-versus-eager result. The 9.2% increase and 60.5% reduction are derived from those displayed timings and apply only to window GPU time. PR #2909 reports 2.8% end-to-end throughput growth with 64 concurrent requests instead.

Step 5 follows `sglang_omni/models/qwen3_omni/components/code2wav_cuda_graph.py:85-117,264-282,673-723,804-888` and `code2wav_scheduler.py:112-143,1307-1345`. `GraphKey` contains batch size, frame count and `window`/`first`/`next` kind. The one-key catalogue is constructed: A replays an exact match, while B changes the row count and misses this catalogue. Other real keys may have their own graphs. Missing or ineligible keys run eagerly; a runtime replay failure disables graphs and re-raises instead of silently retrying eagerly. Capture checks exact output equality before publication.

Step 6 quotes [public PR #1101's historical H200 c16 sweep](https://github.com/sgl-project/sglang-omni/pull/1101#issuecomment-5040716545): eager control 0.575 requests/s, graph replay 0.635 requests/s. Their ratio gives the stage's 10.4% mean-QPS increase. The PR's separate 10.55% paired delta averages per-pair percent changes, so it is not recomputed from the two displayed means. The protocol used ancestor `b4159d2a`, BF16, fresh servers, temperature 0, seed 777, an 800-token Talker cap, 16 warmups and 128 measured requests per arm, and two alternating pairs. Matched audio work stayed within 0.076%. This is not a current-source or universal speedup claim.

Step 7 compares three distinct paths. Qwen uses the mechanisms from Steps 2–6. MiniCPM-o's full-duplex path batches the next chunk per ready session, retains saved decoder work and graphs one repeated chunk-making loop (`sglang_omni/models/minicpm_o/components/tts_runtime.py:47-76,92-121,240-260`; `token2wav/flow.py:408-448,737-800`). Fish batches completed non-streaming requests with padding and trimming, but streaming chunks stay per request (`sglang_omni/models/fishaudio_s2_pro/streaming_vocoder.py:43-66`; `sglang_omni/scheduling/audio_vocoder.py:80-114,116-224`). Fish retains old code frames and a short sound tail to blend window joins, not equivalent execution state (`sglang_omni/scheduling/audio_stream.py:187-239,242-333`). Its production factory does not install the test-only vocoder graph (`sglang_omni/models/fishaudio_s2_pro/stages.py:522-552`). Offline defaults are not applied to these full-duplex or streaming paths.

Step 8 follows Fish S2 Pro's `num_codebooks=10` hand-off. `sglang_omni/models/fishaudio_s2_pro/streaming_vocoder.py:102-106` sends codebook rows 1–10 for each audio frame to the vocoder; `payload_types.py:35-50` defines the payload. The generation loops and the additional row before them belong to Chapter 11. Their call counts and cache layout are deliberately deferred, so this step ends on the ten visible inputs without claiming to explain Dual-AR.
