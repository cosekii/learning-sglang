## Prose · Where this chapter's claims come from

Step 1 constructs a `SimpleScheduler` collection example with four batch slots. A and B are queued at 0 ms; C arrives at 6 ms. With `max_batch_wait_ms=0`, the scheduler takes A and B without waiting for the two empty slots. In the counterfactual five-ms panel, the collection deadline expires at 5 ms, before C arrives, so A and B enter compute five ms later. The timelines omit compute time and every other delay. The five-ms budget is not a shipped MiniCPM-o default or a recommendation.

Step 2 constructs two running rows. A and B occupy both rows in round 1, so C waits. A finishes after that round; B remains in `running_batch`, and C can take the free row if token memory also permits. The two-row cap is a teaching device. MiniCPM-o's talker factory currently passes `max_running_requests=32`, which this small figure does not depict. `generation_batch_policy.py` builds and validates server arguments; `OmniScheduler` owns `waiting_queue`, `running_batch` and admission. Optional prefill coalescing is outside this step.

Step 3 constructs a batch-capable `ReferenceEncodeService` with cap four and zero delay. A, B and C are ready, so non-blocking collection takes all three and leaves one slot empty. D arrives afterward and belongs to the next collection. The shipped defaults remain cap one and zero delay; a larger cap enables this path only when `hook.can_encode_batch()` also succeeds. One batch call returns separate outcomes to the three requests.

Step 4 uses MiniCPM-o's real audio-encoder configuration: request cap eight, zero collection delay and 24,000 charged mel frames. The teaching requests cost five, two and two full 3,000-frame windows. A and B fit at 21,000 frames; adding C would reach 27,000, so `SimpleScheduler` puts C back at the head of `pending_messages` even though three requests are below the count cap. The real budget admits eight full 30-second chunks. These teaching costs are not benchmark observations, and the budget is not a precise FLOP or memory measurement.

Step 5 separates two implementations. MiniCPM-o Code2Wav returns a `SimpleScheduler` with cap 16, zero delay and `batch_wait_when_idle=false`; it collects complete requests and calls `vocode_and_release([A, B])`. Optional `StreamingVocoderBase` subclasses instead ingest each `stream_chunk` into request-local state, select ready participants and call `run_step([A, B])`. Both preserve per-request outputs, but these are not the same message path. The two-request, one-call construction is not a latency or throughput claim.

Step 6 quotes, rather than reruns, the historical H200 FIFO comparison in `batch.md` and PR #2271. With 200 SeedTTS EN requests, client concurrency 16, zero delay, 50 excluded warmups and three mixed-reference repeats, B1 and B8 averaged 4.100 and 5.652 requests/s. The derived improvement is 37.9% relative to B1. This belongs to historical code `89e60d0bf216bacd0e072d79f969550469614662` and its controlled environment. It is not a current-main benchmark or a universal optimum; current MiniCPM-o Code2Wav has cap 16 and a changed implementation.

Step 7 constructs two independent admission examples with cap two and active A and B. At the router, C cannot acquire a permit, so `RouterOverloaded` becomes HTTP 429 before worker dispatch. At the coordinator, two requests already meet `max_in_flight`, so C raises `QueueFullError` before pipeline submit and the OpenAI error mapping returns HTTP 503. Router permits and worker-load guards remain held through response EOF, upstream error or downstream cancellation. These teaching caps are not deployment defaults, and the two status codes belong to different boundaries.
