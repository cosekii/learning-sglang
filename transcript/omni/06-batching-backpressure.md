## Prose · Where this chapter's claims come from

Step 1 constructs a `SimpleScheduler` collection example with four batch slots. A and B are queued at 0 ms; C arrives at 6 ms. With `max_batch_wait_ms=0`, the scheduler takes A and B without waiting for the two empty slots. In the counterfactual five-ms panel, the collection deadline expires at 5 ms, before C arrives, so A and B enter compute five ms later. The timelines omit compute time and every other delay. The five-ms budget is not a shipped MiniCPM-o default or a recommendation.

Step 2 constructs two running rows. A and B occupy both rows in round 1, so C waits. A finishes after that round; B remains in `running_batch`, and C can take the free row if token memory also permits. The two-row cap is a teaching device. MiniCPM-o's talker factory currently passes `max_running_requests=32`, which this small figure does not depict. `generation_batch_policy.py` builds and validates server arguments; `OmniScheduler` owns `waiting_queue`, `running_batch` and admission. Optional prefill coalescing is outside this step.
