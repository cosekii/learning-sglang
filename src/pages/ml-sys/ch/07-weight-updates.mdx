<summary>Where this chapter's claims come from</summary>

This chapter follows `Awesome-ML-SYS-Tutorial/rlhf/sys-design/readme-1.md` and `Awesome-ML-SYS-Tutorial/sglang/latency-accelerate-for-weight-updates/readme.md`. Chapter 6 established that slime waits for `actor_model.async_update_weights()` before the next rollout; this chapter opens that update box.

Step 1 uses the debug note at `latency-accelerate-for-weight-updates/readme.md:556-558,980-1007`. The nominal size is `1,000,000,000 parameters × 2 bytes = 2 GB` in decimal units. The 7.047-second full update, the 0.001-second `ModelRunner` example and the 0.033-second outer call are one author's distributed-update measurements, not a controlled comparison of transport methods.

Step 2 compares the three interfaces at `sys-design/readme-1.md:400-409` and opens the disk route. `update_weights_from_disk` reads a saved checkpoint and eventually calls the model's weight loader. The same checkpoint can serve existing and newly added rollout engines. Storage speed and loader behavior determine its wait; the sources provide no disk timing. The pinned implementation is `sgl-project/sglang@392e441ad17c78b68638f2d959fcf592d19b4834`, `python/sglang/srt/model_executor/model_runner.py:641-694`.

Step 3 follows `latency-accelerate-for-weight-updates/readme.md:232-262,399-412,931-950`. The update group contains one training rank plus the inference TP ranks, so `world_size = 1 + tp_size`. For each parameter, inference allocates a destination, broadcasts the values from rank 0 and calls `load_weights`. Group-rank count is not a count of top-level processes. The pinned `ModelRunner` receive path is `model_runner.py:696-772` at the same SGLang revision.

Step 4 follows `sys-design/readme-1.md:51-60,132-204`. `full_tensor()` assembles the parameter before serialization. `MultiprocessingSerializer.serialize` returns reconstruction handles rather than the tensor payload, and `gather_object` gathers those handles at inference TP rank 0. Each SGLang TP rank deserializes its entry and loads the reconstructed tensor. The fixed sender is `volcengine/verl@0508af25b66e839772fba8e79d97896bf0d843d3`, `verl/workers/sharding_manager/fsdp_sglang.py:160-188`; the receiver is `model_runner.py:774-792,1464-1479` at the pinned SGLang revision. The `[256,1024]` training shards and `[1024,1024]` full tensor follow line 51; line 53 accidentally reverses the two shard labels and is not reproduced.

Step 5 follows `sys-design/readme-1.md:254-272,280-296,329-395`. Slime offloads training weights and optimizer state after training, then restores only one parameter bucket at a time. Within a bucket it broadcasts across PP and EP where needed, gathers TP partitions, removes padding and converts to Hugging Face layout before sending handles. `ray.get(ref)` completes before the converted tensors are cleared. The figure shows the residency boundary but no bucket size or memory saving because the source supplies neither.

Step 6 combines the replacement boundaries at `sys-design/readme-1.md:268-287`, `verl/workers/sharding_manager/fsdp_sglang.py:98-135,164-188` and `latency-accelerate-for-weight-updates/readme.md:451-458,1011-1058`. Generation must not observe a parameter-by-parameter transition, source storage stays alive until the awaited update finishes, and old KV state cannot be reused. Slime resets prefix caches before buckets; verl passes `flush_cache=True` with the last parameter. A partial update failure requires discarding the model. The historical manager's lock, request drain and sleeps are shown as a race-condition workaround, not proof of crash-safe transactional replacement.

<summary>本章说法的出处</summary>

本章依据 `Awesome-ML-SYS-Tutorial/rlhf/sys-design/readme-1.md` 和 `Awesome-ML-SYS-Tutorial/sglang/latency-accelerate-for-weight-updates/readme.md`。第 6 章已经说明 slime 会等 `actor_model.async_update_weights()` 完成再开始下一轮，本章打开这个更新框。

第 1 步使用 `latency-accelerate-for-weight-updates/readme.md:556-558,980-1007` 的调试记录。权重大小按 `1,000,000,000 个参数 × 2 字节 = 2 GB` 计算，采用十进制单位。完整更新 7.047 秒、`ModelRunner` 示例 0.001 秒、外部调用 0.033 秒都是一位作者对 distributed 更新的测量，不是传输方式的对照实验。

第 2 步依据 `sys-design/readme-1.md:400-409` 比较三个接口，并展开磁盘路线。`update_weights_from_disk` 读取保存的 checkpoint，最后调用模型的权重加载器。现有和新加入的 rollout 都能读同一份 checkpoint。等待取决于存储和加载过程，来源没有给出磁盘计时。固定实现为 `sgl-project/sglang@392e441ad17c78b68638f2d959fcf592d19b4834` 的 `python/sglang/srt/model_executor/model_runner.py:641-694`。

第 3 步依据 `latency-accelerate-for-weight-updates/readme.md:232-262,399-412,931-950`。更新组包含 1 个训练 rank 和推理端的 TP rank，所以 `world_size = 1 + tp_size`。每个参数都先由推理端分配接收空间，再从 rank 0 广播数值并调用 `load_weights`。组内 rank 数不等于顶层进程数。固定 `ModelRunner` 接收路径为同一 SGLang 版本的 `model_runner.py:696-772`。

第 4 步依据 `sys-design/readme-1.md:51-60,132-204`。`full_tensor()` 先拼好完整参数，再做序列化。`MultiprocessingSerializer.serialize` 返回的是重建句柄，不是张量数据本体；`gather_object` 再把这些句柄收拢到推理 TP rank 0。每个 SGLang TP rank 反序列化自己的那一项并装入重建的张量。发送端固定为 `volcengine/verl@0508af25b66e839772fba8e79d97896bf0d843d3` 的 `verl/workers/sharding_manager/fsdp_sglang.py:160-188`，接收端为固定 SGLang 版本的 `model_runner.py:774-792,1464-1479`。训练分片 `[256,1024]` 和完整张量 `[1024,1024]` 按第 51 行绘制；第 53 行误把两种分片标签写反，本章不沿用。

第 5 步依据 `sys-design/readme-1.md:254-272,280-296,329-395`。slime 在训练后 offload 训练权重和优化器状态，更新时每次只恢复一个参数桶。桶内按需要做 PP、EP 广播，收集 TP 分片，去掉 padding 并转成 Hugging Face 布局，然后发送句柄。`ray.get(ref)` 完成后才清空转换结果。图中只画显存占用边界；来源没有给出每桶大小或节省量，本章不填数字。

第 6 步合并 `sys-design/readme-1.md:268-287`、`verl/workers/sharding_manager/fsdp_sglang.py:98-135,164-188` 和 `latency-accelerate-for-weight-updates/readme.md:451-458,1011-1058` 的替换边界。生成不能读取逐参数变化的过程；源张量要等到更新调用完成后才释放；旧 KV 不能复用。slime 在分桶前重置 prefix cache，verl 在最后一个参数上传入 `flush_cache=True`。部分更新失败必须弃用这套模型。历史管理器里的锁、请求排空和 sleep 只是竞态规避办法，不证明崩溃安全或事务式替换。
