<summary>Where this chapter's claims come from</summary>

This chapter follows `Awesome-ML-SYS-Tutorial/rlhf/slime/fsdp/readme.md` and `Awesome-ML-SYS-Tutorial/rlhf/sys-design/readme-2-en.md`. Implementation claims use `THUDM/slime@55e41ffef7193fdd4c8bc14720233e446446b1d7`. The memory example is constructed arithmetic, not a training measurement.

Step 1 contrasts full replication with sharding at `fsdp/readme.md:16`. The constructed model has `4,000,000,000` values, with 2-byte weights and 2-byte gradients. Its optimizer convention comes from `readme-2-en.md:21-31`: FP32 master weights (the full-precision update copy), momentum (a running gradient average) and variance (a running squared-gradient average), or `3 × 4 = 12` bytes per value. Thus one full copy uses `4B × (2 + 2 + 12) = 64 GB`, 80% of the shared 80 GB H100 capacity. Eight copies use 512 GB. These numbers describe only the three saved table kinds, not activations or temporary allocations.

Step 2 uses the same source's FSDP alternative: each rank owns a shard of the parameters, gradients and optimizer state (`fsdp/readme.md:16-23`; `readme-2-en.md:43-47`). The equal eight-way split gives `64 ÷ 8 = 8 GB` per rank and 64 GB in aggregate. The stage shows FSDP2's per-parameter DTensor as a logical tensor, a `Shard(0)` placement and each rank's local shard. On a 1D mesh, `fully_shard` uses dim-0 DTensors with `Shard(0)` placement (`pytorch/pytorch@v2.8.0`, `torch/distributed/fsdp/_fully_shard/_fully_shard.py`, `fully_shard`). `Shard(0)` splits tensor dimension 0 across the DP mesh (`torch/distributed/tensor/placement_types.py`, `Shard`). Step 4 all-gathers those parameter shards for computation; Step 7 redistributes each parameter DTensor to `Replicate()` for export (`update_weight_utils.py:45-74` at the pinned revision). The DP mesh determines the shard count: slime computes `dp_size = world_size // cp_size` and passes `dp_mesh` to `fully_shard` (`actor.py:158-186,94-98` at the pinned revision). Eight physical GPUs imply DP 8 only when CP is 1, as in this example.

Step 3 follows the unified `train` entry at `actor.py` and the packing path in `slime/utils/data.py` and `slime/backends/fsdp_utils/data_packing.py`. `process_rollout_data` selects the rank's records. For GRPO/GSPO, `_train_core` repeats each normalized reward by that record's `response_lengths` to form advantages. With dynamic batching, first fit chooses the pack count and DP `MAX` synchronizes it before balanced `pack_sequences` chooses membership. The local `flat_tokens` concatenation is stored as `tokens`; `cu_seqlens` records total-token boundaries. The constructed DP1/CP1 example uses lengths 2, 2, 4, response lengths 1, 1, 2 and cap 4, producing packs A+B and C, `cu_seqlens` [0, 2, 4] and [0, 4], and `grad_accum` [2]. The shipped script instead uses `--max-tokens-per-gpu 9216`.

Step 4 separates the DP1 packing arithmetic from the DP8 memory illustration. It keeps the initial forward account from `fsdp/readme.md:18`: after `optimizer.zero_grad(set_to_none=True)`, the rank holds 7 GB of parameter tables, all-gathers a temporary full layer of unknown size `U`, computes log probabilities and releases it (`actor.py:522-535`). This is not a total-memory or peak figure. The loss path follows `_train_step` (`actor.py:555-702`). This example leaves `use_rollout_logprobs` off: the earlier no-grad, scoring-only actor pass writes `log_probs`, which become the old scores, and the grad-enabled training pass writes `cur_log_probs` so backward can find weight-change directions. Enabling that flag instead selects `rollout_log_probs` as the old scores; the stage does not draw that alternative. `unpack_sequences` uses `cu_seqlens` to recover each record (`data_packing.py:104-146`). The ratio is `exp(log_probs - old_log_probs)`, because `ppo_kl = old_log_probs - log_probs` and `compute_policy_loss` evaluates `(-ppo_kl).exp()` (`actor.py:594,610`; `ppo_utils.py:49-70`). The stage constructs gaps +0.3365 and −0.3567 for Pack 1's A and B, giving ratios 1.40 and 0.70. Step 3 supplies advantages +u and −u. The shipped script sets `eps_clip=0.2` and `eps_clip_high=0.28`, so the clipped ratios are 1.28 and 0.80. Negating both products and taking the larger value gives A −1.1973 and B +0.7483. `sum_of_sample_mean` applies each response mask, averages within each record and sums the records (`actor.py:640,964-978`). Both one-token masks are [1], so Pack 1 gives `L1 = -1.1973 + 0.7483 = -0.4490`. Pack 2 constructs ratios [1.00,1.00] for C's two response tokens. Clipping leaves them unchanged, both advantages are +u, and mask [1,1] gives `L2 = (-u - u) ÷ 2 = -0.9354`. The shipped zero entropy and KL coefficients leave both worked losses unchanged. This step stops at the two actor losses; the next step pre-scales actor loss and follows the resulting gradients.

Step 5 follows the pinned `_train_step` and the main loop in `train.py`. Each pack pre-scales its own loss with `loss = loss * dp_size / global_batch_size`, then calls `loss.backward()` (`actor.py:687-689`). Pack 1 leaves `g1`; Pack 2 adds `g2`, so gradient accumulation holds `g1 + g2` while the weights remain `W0`. Only the end of Pack 2 matches this example's `grad_accum=[2]`; gradient-norm clipping, one `optimizer.step()`, and `zero_grad(set_to_none=True)` then produce `W1` and clear the accumulated gradients (`actor.py:695-702`). The DP1 sequence uses these local `g1` and `g2` symbols without cross-rank averaging. In the separate DP8 reduction view, the FP32 FSDP2 policy sets `reduce_dtype=torch.float32` (`actor.py:1000-1034`), whose default reduce-scatter uses `ReduceOp.AVG` with no extra predivide or postdivide factor (`pytorch/pytorch@v2.8.0`, `_fsdp_collectives.py:605-641`). Thus `R/B` pre-scaling and AVG's `1/R` produce the global-batch mean. The bottom label counts all layers' saved gradient shards: 8 GB ÷ 8 = 1 GB per rank, not one layer's temporary size. After training returns, `train.py:92-94` calls `offload_train()`, restores rollout, and calls `actor_model.update_weights()` in that order. With `offload_train` enabled, `actor.py:270-281` moves the model and optimizer to CPU; rollout restoration is not drawn. Step 7 opens the bucketed weight-export path. Gradient clipping, metric aggregation, checkpoint saves and rollout restoration are outside this compact stage.

Step 6 treats 8 GB as the complete logical training-state bill, including the gradient shard when gradients are stored. It is not a permanent forward residency floor: Step 4 starts at 7 GB after `zero_grad`. Peak memory still exceeds the full 8 GB bill because temporary layers and training intermediates also need space. Activations vary with batch size (`readme-2-en.md:31`). The source's formula with the largest fully materialized unit is explicitly for FSDP1 Stage 3 (`readme-2-en.md:93-107`), so the stage uses it only to identify memory categories. It does not present that formula as an exact FSDP2/slime measurement or assign values to temporary allocations.

Step 7 follows `fsdp/readme.md:134-140` and the executable updater at `update_weight_utils.py:45-74` in the pinned slime revision. The updater iterates model-state weights, redistributes each DTensor to `Replicate()` and gathers full tensors into size-bounded buckets. It waits for asynchronous results before handing a bucket to Ch. 7 Step 5's one-bucket-at-a-time transport. Ch. 7 Step 6 then waits for a complete version and rejects old KV. Gradients and optimizer state are not exported, and the whole training model is not materialized at once. The deep dive records the shipped 512 MiB flush threshold from `scripts/run-qwen3-4B-fsdp.sh:93-108`; it is a flushing threshold, not a hard memory cap. The closing question leads to Chapter 9's FP8 topic without claiming an FP8 mechanism or speedup here.

<summary>本章说法的出处</summary>

本章依据 `Awesome-ML-SYS-Tutorial/rlhf/slime/fsdp/readme.md` 和 `Awesome-ML-SYS-Tutorial/rlhf/sys-design/readme-2-en.md`。实现结论固定到 `THUDM/slime@55e41ffef7193fdd4c8bc14720233e446446b1d7`。显存示例是构造算式，不是训练实测。

第 1 步依据 `fsdp/readme.md:16` 对照完整复制与分片。构造模型有 `4,000,000,000` 个数值，权重和梯度都按 2 字节计算。优化器约定来自 `readme-2-en.md:21-31`：FP32 master 权重（用于更新的全精度副本）、momentum（梯度的滑动平均值）和 variance（梯度平方的滑动平均值），即每个数值 `3 × 4 = 12` 字节。因此一份完整训练表占 `4B × (2 + 2 + 12) = 64 GB`，是共享 H100 80 GB 容量的 80%；8 份占 512 GB。这些数字只算三类保存的表，不含激活和临时分配。

第 2 步使用同一来源的 FSDP 方案：每个 rank 拥有参数、梯度和优化器状态的一片（`fsdp/readme.md:16-23`；`readme-2-en.md:43-47`）。平均分成 8 份得到每个 rank `64 ÷ 8 = 8 GB`，合计仍为 64 GB。舞台把 FSDP2 的逐参数 DTensor 画成逻辑张量、`Shard(0)` placement 和各 rank 的本地分片。在一维 mesh 上，`fully_shard` 用 `Shard(0)` placement 把参数表示为按第 0 维分片的 DTensor（`pytorch/pytorch@v2.8.0` 的 `torch/distributed/fsdp/_fully_shard/_fully_shard.py` 中 `fully_shard`）。`Shard(0)` 把张量第 0 维分到 DP mesh 上（`torch/distributed/tensor/placement_types.py` 中 `Shard`）。第 4 步 all-gather 这些参数分片用于计算；第 7 步把每个参数 DTensor 重新分布为 `Replicate()` 用于导出（固定版本的 `update_weight_utils.py:45-74`）。分片数由 DP mesh 决定：slime 计算 `dp_size = world_size // cp_size`，并把 `dp_mesh` 传给 `fully_shard`（固定版本的 `actor.py:158-186,94-98`）。本例取 CP 1，所以 8 张物理 GPU 才对应 DP 8。

第 3 步跟随 `actor.py` 的统一 `train` 入口，以及 `slime/utils/data.py` 和 `slime/backends/fsdp_utils/data_packing.py` 的打包路径。`process_rollout_data` 选出这个 rank 的记录。GRPO/GSPO 在 `_train_core` 中按每条记录的 `response_lengths` 重复归一化分数，形成 advantages。动态 batch 先用 first fit 决定包数，经 DP `MAX` 同步，再由均衡 `pack_sequences` 决定成员。局部 `flat_tokens` 拼接后存为 `tokens`，`cu_seqlens` 记录总 token 边界。构造的 DP1/CP1 例子取长度 2、2、4，回答长度 1、1、2 和 cap 4，得到 A+B 与 C 两包，`cu_seqlens` 分别为 [0, 2, 4] 和 [0, 4]，`grad_accum` 为 [2]。自带脚本实际使用 `--max-tokens-per-gpu 9216`。

第 4 步把 DP1 打包算式与 DP8 显存示例分开。它保留 `fsdp/readme.md:18` 的初始 forward 账：`optimizer.zero_grad(set_to_none=True)` 后，rank 持有 7 GB 参数表，all-gather 一个大小未知的临时完整层 `U`，算出 log probability 后释放（`actor.py:522-535`）。这不是总显存或峰值。loss 路径跟随 `_train_step`（`actor.py:555-702`）。本例关闭 `use_rollout_logprobs`：较早的 no-grad actor 计算只评分并写入 `log_probs`，作为旧分数；带梯度的训练计算写入 `cur_log_probs`，让 backward 能求出权重变化方向。启用这个 flag 时，旧分数改用 `rollout_log_probs`，图上没有画这条替代路径。`unpack_sequences` 按 `cu_seqlens` 还原每条记录（`data_packing.py:104-146`）。由于 `ppo_kl = old_log_probs - log_probs`，`compute_policy_loss` 中的 `(-ppo_kl).exp()` 就是 `exp(log_probs - old_log_probs)`（`actor.py:594,610`；`ppo_utils.py:49-70`）。图中给第 1 包的 A、B 构造 +0.3365 和 −0.3567 的差值，得到 ratio 1.40 和 0.70。第 3 步提供 advantage +u 和 −u。自带脚本设置 `eps_clip=0.2`、`eps_clip_high=0.28`，所以裁剪后是 1.28 和 0.80。两个乘积取负再取大值，A 得 −1.1973，B 得 +0.7483。`sum_of_sample_mean` 应用 response mask，在每条记录内取均值，再把记录相加（`actor.py:640,964-978`）。两个单 token mask 都是 [1]，所以第 1 包得到 `L1 = -1.1973 + 0.7483 = -0.4490`。第 2 包为 C 的两个回答 token 构造 ratio [1.00,1.00]，clip 不改变它们；两个 advantage 都是 +u，mask [1,1] 给出 `L2 = (-u - u) ÷ 2 = -0.9354`。自带脚本的 entropy 和 KL 系数都为 0，不改变两包的构造 loss。本步只算两个 actor loss；下一步预缩放 actor loss，并跟随由此得到的梯度。

第 5 步跟随固定版本的 `_train_step` 和 `train.py` 主循环。每包先执行 `loss = loss * dp_size / global_batch_size`，再调用 `loss.backward()`（`actor.py:687-689`）。第 1 包留下 `g1`，第 2 包加上 `g2`，所以梯度累加保存 `g1 + g2`，权重仍是 `W0`。只有第 2 包结束命中本例的 `grad_accum=[2]`；随后依次执行梯度范数裁剪、一次 `optimizer.step()` 和 `zero_grad(set_to_none=True)`，得到 `W1` 并清空累加梯度（`actor.py:695-702`）。DP1 序列使用这里的本地 `g1`、`g2` 符号，不做跨 rank 平均。在独立的 DP8 归约视图中，FP32 FSDP2 策略设置 `reduce_dtype=torch.float32`（`actor.py:1000-1034`），默认 reduce-scatter 使用 `ReduceOp.AVG`，没有额外的归约前或归约后除数（`pytorch/pytorch@v2.8.0` 的 `_fsdp_collectives.py:605-641`）。因此 `R/B` 预缩放与 AVG 的 `1/R` 合起来得到全批均值。底部标签计算所有层保存的梯度分片：8 GB ÷ 8 = 每个 rank 1 GB，不是本层临时大小。训练返回后，`train.py:92-94` 依次调用 `offload_train()`、恢复 rollout，再调用 `actor_model.update_weights()`。启用 `offload_train` 时，`actor.py:270-281` 把模型和优化器移到 CPU；图中不画 rollout 恢复。第 7 步展开按桶导出权重的路径。梯度裁剪、指标汇总、checkpoint 保存和 rollout 恢复不放进这张紧凑舞台。

第 6 步把 8 GB 写成完整逻辑训练状态账，包括保存梯度时的梯度分片。它不是 forward 的永久常驻下限：第 4 步在 `zero_grad` 后从 7 GB 开始。临时层和训练中间结果仍需空间，所以峰值大于完整 8 GB 训练账。激活随 batch 大小变化（`readme-2-en.md:31`）。来源包含最大完整 unit 的公式明确针对 FSDP1 Stage 3（`readme-2-en.md:93-107`），所以图中只借它辨认显存类别，不把该公式当成 FSDP2/slime 的精确测量，也不给临时分配填值。

第 7 步依据 `fsdp/readme.md:134-140` 和固定 slime 版本的实际更新器 `update_weight_utils.py:45-74`。更新器遍历模型状态里的权重，把每个 DTensor `redistribute` 到 `Replicate()`，再把完整张量装进大小受限的桶。异步结果完成后，按第 7 章第 5 步每次交接一桶。第 7 章第 6 步再等待完整版本更新完并拒绝旧 KV。导出不包含梯度和优化器状态，也不会一次拼出整套训练模型。深入讲解记录自带脚本 `scripts/run-qwen3-4B-fsdp.sh:93-108` 的 512 MiB 冲刷阈值；它不是严格显存上限。结尾引向第 9 章的 FP8 主题，本步不宣称 FP8 的机制或加速效果。
