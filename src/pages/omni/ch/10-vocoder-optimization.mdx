<summary>Where this chapter's claims come from</summary>

Step 1 follows Qwen3-Omni's default streaming Code2Wav windows in `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:79-109,999-1011`. A later stateless window reads 25 earlier frames and 10 new frames, then emits only the 10 new frames. Learning SGLang Ch. 20 Steps 1–3 established that those 10 frames represent 800 ms of playback. The three map entries are cross-request batching, retained codec state and exact-shape CUDA graphs; later steps explain each one. The frame counts describe input work, not elapsed time.

Step 2 follows `sglang_omni/scheduling/streaming_vocoder.py:819-842` and `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:999-1079`. The constructed comparison changes three independent `[B=1,T=10]` first-window calls into one `[B=3,T=10]` call. Real groups also require matching first/later kind and slot/stateless mode. They contain at most eight replay rows and do not pad unlike lengths into one replay. `tests/unit_test/qwen3_omni/test_code2wav_batching.py:111-191` checks shared rows and the first/later boundary. The 3→1 count is not a timing result.

Step 3 follows `sglang_omni/models/qwen3_omni/components/codec_state_pool.py:13-24,63-115` and `code2wav_scheduler.py:296-327,999-1011,1283-1300`. A slot holds K/V rings, convolution histories, overlap samples and stream position. The first window writes state; a later slot-backed window reads only 10 new frames instead of 25 old plus 10 new. A request without a free slot remains stateless for life, and a short stream ending before its first threshold window decodes statelessly. The 35→10 comparison counts input frames, not latency or memory savings.

Step 4 quotes [public PR #2909](https://github.com/sgl-project/sglang-omni/pull/2909), measured on Qwen3-Omni colocated BF16 on H200 with eight rows and one graph replay, median of 20 timings. The first window rises from 3,656.3 to 3,992.0 µs because it writes state; the later window falls from 10,777.5 to 4,255.3 µs. Both arms use graph replay, so this is a retained-state comparison, not a graph-versus-eager result. The 9.2% increase and 60.5% reduction are derived from those displayed timings and apply only to window GPU time. PR #2909 reports 2.8% end-to-end c64 QPS growth instead.

Step 5 follows `sglang_omni/models/qwen3_omni/components/code2wav_cuda_graph.py:85-117,264-282,673-723,804-888` and `code2wav_scheduler.py:112-143,1307-1345`. `GraphKey` contains batch size, frame count and `window`/`first`/`next` kind. The one-key catalogue is constructed: A replays an exact match, while B changes the row count and misses this catalogue. Other real keys may have their own graphs. Missing or ineligible keys run eagerly; a runtime replay failure disables graphs and re-raises instead of silently retrying eagerly. Capture checks exact output equality before publication.

Step 6 quotes [public PR #1101's historical H200 c16 sweep](https://github.com/sgl-project/sglang-omni/pull/1101#issuecomment-5040716545): eager control 0.575 requests/s, graph replay 0.635 requests/s. Their ratio gives the stage's 10.4% mean-QPS increase. The PR's separate 10.55% paired delta averages per-pair percent changes, so it is not recomputed from the two displayed means. The protocol used ancestor `b4159d2a`, BF16, fresh servers, temperature 0, seed 777, an 800-token Talker cap, 16 warmups and 128 measured requests per arm, and two alternating pairs. Matched audio work stayed within 0.076%. This is not a current-source or universal speedup claim.

Step 7 compares three distinct paths. Qwen uses the mechanisms from Steps 2–6. MiniCPM-o native batches one unit per ready session, retains Flow/HiFT caches and graphs only its internal Flow chunk loop (`tts_runtime.py:47-76,92-121,240-260`; `token2wav/flow.py:408-448,737-800`). Fish batches completed non-streaming requests with padding and trimming, but streaming chunks stay per request (`streaming_vocoder.py:43-66`; `scheduling/audio_vocoder.py:80-114,116-224`). Fish retains old code frames and crossfade samples, not equivalent execution state (`scheduling/audio_stream.py:187-239,242-333`). Its production factory does not install the test-only vocoder graph (`fishaudio_s2_pro/stages.py:522-552`). Offline defaults are not applied to these native or streaming paths.

Code references in this chapter pin to `sglang-omni origin/main@3a31bd72e034db37ce5115a03dd4827b449683be`. The chapter reads source and public results; it does not run a model or benchmark.

<summary>本章说法的出处</summary>

第 1 步依据 Qwen3-Omni 默认的流式 Code2Wav 窗口，见 `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:79-109,999-1011`。后续无状态窗口读取 25 帧旧内容和 10 帧新内容，只输出那 10 帧新内容。Learning SGLang 第 20 章第 1–3 步已经说明，这 10 帧代表 800 ms 播放。地图三项是跨请求 batching、保留 codec 状态和精确形状 CUDA graph，后续步骤分别解释。帧数描述输入工作量，不是耗时。

第 2 步依据 `sglang_omni/scheduling/streaming_vocoder.py:819-842` 和 `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:999-1079`。构造对照把三次独立 `[B=1,T=10]` 首个窗口调用变成一次 `[B=3,T=10]` 调用。真实分组还要求首个/后续类型和 slot/无状态模式匹配，每次最多重放八行，不把不同长度补进同一次 replay。`tests/unit_test/qwen3_omni/test_code2wav_batching.py:111-191` 检查共享行和首个/后续边界。3→1 是调用数，不是耗时结果。

第 3 步依据 `sglang_omni/models/qwen3_omni/components/codec_state_pool.py:13-24,63-115` 和 `code2wav_scheduler.py:296-327,999-1011,1283-1300`。slot 保存 K/V 环、卷积历史、重叠样本和流位置。首个窗口写入状态；后续 slot 窗口只读取 10 帧新内容，不再读取 25 帧旧内容加 10 帧新内容。没有空 slot 的请求始终走无状态路径，首个阈值窗口前结束的短流也无状态解码。35→10 比较输入帧数，不是延迟或显存收益。

第 4 步引用[公开 PR #2909](https://github.com/sgl-project/sglang-omni/pull/2909)，条件是 Qwen3-Omni 同卡 BF16、H200、8 行、一次 graph replay、20 次取中位数。首窗口写入状态，从 3,656.3 升到 3,992.0 µs；后续窗口从 10,777.5 降到 4,255.3 µs。两边都用 graph replay，所以这是保留状态对照，不是 graph 对 eager。9.2% 增幅和 60.5% 降幅由展示的耗时推导，只适用于窗口 GPU 时间。PR #2909 的端到端 c64 QPS 增幅是 2.8%。

第 5 步依据 `sglang_omni/models/qwen3_omni/components/code2wav_cuda_graph.py:85-117,264-282,673-723,804-888` 和 `code2wav_scheduler.py:112-143,1307-1345`。`GraphKey` 包含 batch 大小、帧数和 `window`/`first`/`next` 类型。单 key 目录是构造示例：A 完全匹配后 replay，B 改变行数，在此目录 miss。真实其他 key 可能有自己的 graph。缺少或不合格 key 走 eager；运行时 replay 失败会禁用 graphs 并抛错，不会悄悄重试 eager。capture 发布前检查输出完全相等。

第 6 步引用[公开 PR #1101 的历史 H200 c16 对照](https://github.com/sgl-project/sglang-omni/pull/1101#issuecomment-5040716545)：eager 对照 0.575 requests/s，graph replay 0.635 requests/s。两者之比得到图上的 10.4% 平均 QPS 增幅。PR 另报的 10.55% paired delta 是逐对百分比变化的均值，不能由两个展示均值重算。协议使用 ancestor `b4159d2a`、BF16、新 server、temperature 0、seed 777、Talker 上限 800 token，每方预热 16 个并测量 128 个请求，做两轮交替对照。匹配音频工作量相差不超过 0.076%。这不是当前源码或通用加速声明。

第 7 步对照三条不同路径。Qwen 使用第 2–6 步的机制。MiniCPM-o native 把每个就绪 session 的一个单元组成 batch，保留 Flow/HiFT caches，只把内部 Flow chunk 循环接入 graph（`tts_runtime.py:47-76,92-121,240-260`；`token2wav/flow.py:408-448,737-800`）。Fish 通过补位和裁切 batch 已完成的非流式请求，流式 chunks 仍逐请求运行（`streaming_vocoder.py:43-66`；`scheduling/audio_vocoder.py:80-114,116-224`）。Fish 保留旧 code frames 和 crossfade 样本，不是等价的执行状态（`scheduling/audio_stream.py:187-239,242-333`）。生产 factory 没有接入测试展示的 vocoder graph（`fishaudio_s2_pro/stages.py:522-552`）。离线默认值不套到这些 native 或流式路径。

本章代码出处固定到 `sglang-omni origin/main@3a31bd72e034db37ce5115a03dd4827b449683be`。本章只读源码和公开结果，没有运行模型或 benchmark。
