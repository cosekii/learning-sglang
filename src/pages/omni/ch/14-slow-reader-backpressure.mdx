<summary>Where this chapter's claims come from</summary>

Step 1 uses a constructed ten-second response whose reader has taken four seconds. The reader takes audio at playback speed, while generation can be faster than real time; once the socket buffer fills, unread audio accumulates in the coordinator queue (Ch. 8 Step 3). The arithmetic describes the coordinator's internal 24 kHz float32 payload: `24,000 × 4 × 6 = 576,000 B`. HTTP audio output is mono 16-bit, so these bytes are not the raw PCM delivery format. A finished request releases its generation-capacity slot, but streamed audio can remain in the API process until the client reads it (`docs/cookbook/qwen3_tts/tuning.md:22-26`; `sglang_omni/pipeline/coordinator.py:103-109,213-223`). Socket buffering means bytes already handed to the operating system or HTTP runtime. Those bytes also wait for the client, but they no longer belong to the coordinator's ledger.

Step 2 shows the shipped `stream_delivery.max_total_backlog_bytes` default: 1 GiB per coordinator/API process, with `none` disabling the cap (`sglang_omni/config/schema.py:641-648,793-796`; `docs/cookbook/qwen3_tts/tuning.md:24-28`). The accounting sums only top-level `bytes` values in a message payload. The constructed six-byte audio payload and 100-character string therefore contribute six bytes, not 106 (`sglang_omni/pipeline/coordinator.py:91-100`). The 3.1-hour comparison uses the same internal 24 kHz float32 payload, not the mono 16-bit HTTP output. Socket buffers are bytes already handed to the operating system or HTTP runtime, so they remain outside this ledger. Text, total process memory and other API processes are also outside it.

Step 3 defines reader idleness from coordinator queue reads, not playback. `queue.get()` subtracts the delivered payload from both ledgers and sets `reader_idle_since_s` to the current monotonic time. A later produced chunk increases the backlog without changing that timestamp; when an empty backlog first becomes nonempty, the producer starts the idle clock (`sglang_omni/pipeline/coordinator.py:103-109,497-520,1088-1096`; `tests/unit_test/pipeline/test_coordinator.py:1599-1620`). The two-second timestamps are constructed.

Step 4 reproduces the unit test's 12 B example. `req-idle` holds 4 B with the older reader timestamp; `req-behind` holds 8 B with a fresher reader. Another 4 B for `req-behind` makes 16 B. The coordinator fails `req-idle`, subtracts its 4 B and leaves 12 B. Selection uses the oldest `reader_idle_since_s` among streams with positive backlog, not the largest backlog, and the cap triggers only while the total is strictly greater (`sglang_omni/pipeline/coordinator.py:1102-1131`; `tests/unit_test/pipeline/test_coordinator.py:1516-1539`). The tiny byte counts and adjusted timestamps are test values.

Step 5 reproduces the second 12 B unit test. The streams hold 2, 4 and 4 B; the fresh stream adds 6 B, making 16 B. Failing the oldest 2 B stream leaves 14 B, still over the cap. Failing the next-oldest 4 B stream leaves 10 B and increments `failed_stream_count` to two (`sglang_omni/pipeline/coordinator.py:1102-1131`; `tests/unit_test/pipeline/test_coordinator.py:1544-1569`). One eviction is not guaranteed to restore the budget.

Step 6 uses the running/finished unit test's 10 B cap, so its constructed 12 B queue is already over the limit. The coordinator fails the whole stream rather than dropping selected chunks, because dropping selected chunks would corrupt its audio. On a cap failure, a still-owned running request enters the failure completion path, broadcasts abort and sends the failure to its stream queue. If generation already finished, no running generation remains to abort (`sglang_omni/pipeline/coordinator.py:940-967,1027-1029,1098-1144`; `tests/unit_test/pipeline/test_coordinator.py:1465-1505`). Terminal waveforms use the same accounting (`tests/unit_test/pipeline/test_coordinator.py:1691-1715`), and a terminal waveform that exceeds the cap can fail its own stream (`tests/unit_test/pipeline/test_coordinator.py:1738-1762`).

Step 7 separates failure output before the first audio frame from output after the response starts. Before the first audio frame, HTTP SSE and raw-audio requests return a JSON HTTP 503 (`sglang_omni/serve/openai_api.py:2202-2260,1945-1967`; `sglang_omni/serve/speech_errors.py:126-138`). After SSE starts, the reader instead receives an error event containing `The request queue is full.`; the implementation marks `partial_audio=true, action=discard` when audio already went out (`sglang_omni/serve/speech_streaming.py:202-228`). A raw response has no general error envelope and can only end early. Speech WebSocket uses an error event and its own completion handling. The protocol exits are also documented in `docs/cookbook/qwen3_tts/tuning.md:24-28`. This cap still does not refuse new requests at admission.

Step 8 separates two close cases. With no cap failure, 12 B remains unread; closing aborts work only while its coordinator work record remains, then removes the stream queue, future and backlog and releases the ID (`sglang_omni/pipeline/coordinator.py:497-553`; `tests/unit_test/pipeline/test_coordinator.py:1625-1638`; Ch. 3 Step 2). After a cap failure, eviction has already removed all counted audio bytes and drained the audio messages. The error remains in the stream queue and the ID stays reserved until the reader takes the error or closes (`sglang_omni/pipeline/coordinator.py:1116-1144`; `tests/unit_test/pipeline/test_coordinator.py:1491-1505`). The closing question moves to the planned Chapter 15: when two API processes share one public URL, which process receives the next request?

Code references in this chapter pin to `sglang-omni origin/main@9725235249df851281d4dc62a04b2d34b02ac0fe`. The chapter reads source and unit tests; it does not run a model or measure a server.

<summary>本章说法的出处</summary>

第 1 步构造一段 10 秒回答，读者只取走 4 秒。客户端按播放速度读取，生成却可以快于实时；socket 缓冲填满后，未读声音就积在 coordinator 队列里（第 8 章第 3 步）。算式只描述 coordinator 队列里的 internal 24 kHz float32 payload：`24,000 × 4 × 6 = 576,000 B`。HTTP 输出是 mono 16-bit，所以这些字节不是 raw PCM 的交付格式。请求完成后会释放生成容量名额，但流式声音可以留在 API 进程里，直到客户端读取（`docs/cookbook/qwen3_tts/tuning.md:22-26`；`sglang_omni/pipeline/coordinator.py:103-109,213-223`）。socket 缓冲是已经交给操作系统或 HTTP runtime 的字节。它们也在等客户端，但不再属于 coordinator 的账本。

第 2 步展示随仓库发布的 `stream_delivery.max_total_backlog_bytes` 默认值：每个 coordinator／API 进程 1 GiB，`none` 关闭上限（`sglang_omni/config/schema.py:641-648,793-796`；`docs/cookbook/qwen3_tts/tuning.md:24-28`）。记账只累加消息内容顶层的 `bytes` 值，所以构造的 6 字节声音和 100 字符文字合计仍只计 6 字节，不是 106（`sglang_omni/pipeline/coordinator.py:91-100`）。3.1 小时的比较仍用 internal 24 kHz float32 payload，不用 mono 16-bit 的 HTTP 输出。socket 缓冲是已经交给操作系统或 HTTP runtime 的字节，所以不在这份账里。文字、进程总内存和其他 API 进程也不计入。

第 3 步用 coordinator 的队列读取定义空闲，不用播放位置。`queue.get()` 从两本账减去交付负载，并把 `reader_idle_since_s` 设为当前 monotonic 时刻。之后新生成的 chunk 增加积压，却不改这个时间；空积压第一次变为非空时，生产者会启动空闲钟（`sglang_omni/pipeline/coordinator.py:103-109,497-520,1088-1096`；`tests/unit_test/pipeline/test_coordinator.py:1599-1620`）。图上的两秒时刻是构造值。

第 4 步复现单元测试的 12 B 算例。`req-idle` 有 4 B，读取时间戳更老；`req-behind` 有 8 B，读取更新。`req-behind` 再增加 4 B，总量变成 16 B。coordinator 让 `req-idle` 失败，减去它的 4 B，留下 12 B。实现从积压大于 0 的流里选择最老的 `reader_idle_since_s`，不是选择最大积压；只有总量严格大于上限才触发（`sglang_omni/pipeline/coordinator.py:1102-1131`；`tests/unit_test/pipeline/test_coordinator.py:1516-1539`）。这些微小字节数和调整后时间戳都是测试值。

第 5 步复现第二个 12 B 单元测试。三路流分别有 2、4、4 B，最新读取的流再增加 6 B，总量变成 16 B。最老的 2 B 流失败后还剩 14 B，仍然超限；再让次老的 4 B 流失败，剩下 10 B，`failed_stream_count` 增加到 2（`sglang_omni/pipeline/coordinator.py:1102-1131`；`tests/unit_test/pipeline/test_coordinator.py:1544-1569`）。一次淘汰不保证能恢复预算。

第 6 步使用运行中／已完成单元测试的 10 B 上限，所以构造的 12 B 队列已经超过上限。coordinator 让整条流失败，而不是只丢选中的 chunks，因为只丢这些 chunks 会弄坏声音。超过上限时，仍由 coordinator 持有的运行中请求进入失败完成路径，广播 abort，并把失败送入流队列。生成已经完成时，没有还在运行的生成可中止（`sglang_omni/pipeline/coordinator.py:940-967,1027-1029,1098-1144`；`tests/unit_test/pipeline/test_coordinator.py:1465-1505`）。完成消息中的声音使用同一记账（`tests/unit_test/pipeline/test_coordinator.py:1691-1715`），超过上限的完成声音也能让自己的流失败（`tests/unit_test/pipeline/test_coordinator.py:1738-1762`）。

第 7 步分开首个声音之前和响应开始之后的失败输出。首个声音之前，HTTP SSE 和 raw audio 请求返回 JSON HTTP 503（`sglang_omni/serve/openai_api.py:2202-2260,1945-1967`；`sglang_omni/serve/speech_errors.py:126-138`）。SSE 开始后，读者改为收到含 `The request queue is full.` 的 error 事件；已经发出声音时，实现标记 `partial_audio=true, action=discard`（`sglang_omni/serve/speech_streaming.py:202-228`）。raw 响应没有通用错误外壳，只能提前结束。语音 WebSocket 使用 error 事件和自己的完成处理。这些协议出口也见 `docs/cookbook/qwen3_tts/tuning.md:24-28`。这个上限仍不在 admission 拒绝新请求。

第 8 步分开两种关闭情况。没有上限失败时，12 B 仍未读取；关闭只在 coordinator 的工作记录还在时中止工作，然后删除流队列、future 和积压，并释放 ID（`sglang_omni/pipeline/coordinator.py:497-553`；`tests/unit_test/pipeline/test_coordinator.py:1625-1638`；第 3 章第 2 步）。上限失败后，淘汰已经减去全部计入的声音字节并清空声音消息。错误留在流队列里，ID 仍被占用，直到读者取走错误或关闭（`sglang_omni/pipeline/coordinator.py:1116-1144`；`tests/unit_test/pipeline/test_coordinator.py:1491-1505`）。图末问题交给规划中的第 15 章：两个 API 进程共用一个公开网址时，谁接收下一个请求？
