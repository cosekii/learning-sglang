<summary>Where this chapter's claims come from</summary>

Step 1 counts the shipped startup shapes. Text-only mode defines six stages in one `pipeline` process on one GPU and still accepts text, image, audio or video input (`sglang_omni/models/qwen3_omni/config.py:136-147,257-265,412-422`; `docs/cookbook/qwen3_omni.md:46-57,206-208`). Default speech defines seven stages, each in its own process: image encoder, audio encoder, thinker and code2wav use GPU 0, talker uses GPU 1, and preprocessing and decode are CPU stages (`config.py:268-318,425-452`). These counts exclude the HTTP server and coordinator.

Step 2 separates server mode from requested output. Both modes accept multimodal input (`docs/cookbook/qwen3_omni.md:206-208`). Text-only joins active input branches at `mm_aggregate`; the speech thinker merges them itself (`sglang_omni/models/qwen3_omni/config.py:136-189,212-254`). A speech request with `modalities: ["text"]` terminates at decode and excludes talker; adding `"audio"` also terminates at code2wav (`sglang_omni/models/qwen3_omni/request_builders.py:200-261`; `tests/unit_test/qwen3_omni/test_pipeline.py:898-930,1935-1947`). The public default is text output, and a text-only server returns no audio when audio is requested (`docs/basic_usage/omni.md:22,154-170,199-200,359,386-395`).

Step 3 preserves the public PR #1235 topology from Chapter 8 Step 1: H200s, thinker TP2 and code2wav on one thinker GPU. At concurrency eight, moving only the talker from that same GPU to a third GPU reduced mean-of-two p90 first audio from 2.680 to 1.439 seconds, about 46%. The exact raw values come from PR #1235; the pinned tuning guide publishes rounded ranges and a separate single-stream result where isolation improved first audio but increased end-to-end latency by 14–17% (`docs/cookbook/qwen3_omni/tuning.md:52-69`). Step 8's TP1 plan is a different topology and needs its own comparison.

Step 4 starts with the H100 BF16 colocated config's declared `2 + 2 + 78 + 10 + 2 = 94%` (`examples/configs/qwen3_omni_colocated_h100_bf16.yaml:1-20`). The thinker factory defaults `encoder_mem_reserve` to 0.05. With no explicit `thinker.engine.mem_fraction_static`, it subtracts five whole-card percentage points before deriving the AR budget, giving `0.78 − 0.05 = 0.73`; this reserve is headroom for encoder work outside thinker AR, not the separate 2% + 2% encoder stage declarations (`sglang_omni/models/qwen3_omni/stages.py:155-215,1230-1243,1358-1373`; `sglang_omni/scheduling/sglang_backend/server_args_builder.py:176-210`). A matching explicit fraction skips the reserve, a conflicting fraction is rejected, and a byte-sized KV declaration skips the fraction adjustment (`tests/unit_test/qwen3_omni/test_sglang_ar_budget.py:491-511,540-562`; `stages.py:1384-1402`). Colocation requires one common GPU, TP 1, no in-worker process replicas and a declared budget for every GPU stage (`sglang_omni/models/qwen3_omni/placement.py:55-60,84-108,122-187`). These are configuration arithmetic and validation rules, not measured occupancy.

Step 5 compares BF16, FP8 and INT4. The compatibility matrix permits each precision for text-only output, separate thinker/talker cards at TP1 or TP2, or one shared card at TP1 (`docs/cookbook/qwen3_omni.md:25-44`). BF16 is the default. The FP8 checkpoint supplies precision config for thinker and talker AR; `--dtype fp8` is not the selection mechanism (`docs/cookbook/qwen3_omni.md:153-169`; `sglang_omni/models/weight_loader.py:19-42`). The INT4 checkpoint uses 4-bit groups of 128 thinker weights while talker AR and code2wav remain BF16 (`docs/cookbook/qwen3_omni.md:181-195`). The cookbook explicitly names code2wav's BF16 precision for INT4. The implementation also defaults omitted code2wav `dtype` to BF16 for the other rows (`sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:146-154,1230-1260`; `sglang_omni/models/weight_loader.py:19-26`). The approximately 60, 40 and 30 GB values and their 50%/25% reductions appear in a single-GPU H100/H20 section, but their exact quantity—weights alone, loaded stages, runtime peak or whole-server footprint—is unstated. They are not measured per-card budgets or local footprint, latency or quality measurements (`docs/cookbook/qwen3_omni.md:196-200`).

Step 6 applies the shipped replica2 config. The thinker defaults to 64 running requests; each talker engine defaults to 32 (`sglang_omni/models/qwen3_omni/stages.py:1276-1286`; `sglang_omni/models/qwen3_omni/config.py:37,454-496`). Two talker replicas make each code2wav process compute `codec_state_slots = 32 × 2 = 64` for its own independent pool, covering the streams the talkers can run (`config.py:468-476`; `tests/unit_test/qwen3_omni/test_colocation_config.py:177-203`; `sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:1284-1299`). A full pool falls back to stateless left-context decoding instead of rejecting the stream (`code2wav_scheduler.py:296-314`). The config places talker/code2wav replica 0 on GPU 1 and replica 1 on GPU 2, with `12.3% + 1.4% = 13.7%` declared per replica GPU (`examples/configs/qwen3_omni_speech_replica2.yaml:1-42`). This is per-process configuration capacity, not one deployment-wide pool, a throughput measurement or a binding-contract guarantee under a custom replica policy.

Step 7 separates health from performance. Readiness sends a small image, one second of audio and a short instruction, with at most eight new tokens per token-generating stage (`docs/cookbook/qwen3_omni.md:202-204`; `sglang_omni/models/qwen3_omni/config.py:328-366`). Video, large batches and other input sizes may still warm later (`docs/basic_usage/omni.md:345-349`). A comparison first resolves the config, then holds input, sampling, hardware and warmup fixed while changing one deployment choice (`docs/basic_usage/process_topology.md:52-53`; Chapter 8 Steps 6 and 8). The documented sweep `--concurrencies 1,16 --repeats 5 --generate-only` gives ten measured runs per arm; raw repeats, failures and memory stay in the comparison. First audio and server time stay separate from listener stalls and the Chapter 12 stop/response clocks. The benchmark notes that p99 needs at least 100 measured requests in the underlying cohort, not merely a particular number of runs (`benchmarks/README.md:249-288`; `benchmarks/eval/benchmark_omni_seedtts.py:504-505,552-561`).

Step 8 constructs one TP1 starting hypothesis for eight concurrent spoken requests: default BF16 speech, text and audio output, input encoders, thinker and code2wav on GPU 0, and talker alone on GPU 1. This is motivated by Step 3's different H200/TP2 evidence and requires a local A/B comparison. Eight is below the 32-request talker cap, leaving `32 − 8 = 24` unallocated cap slots, so the example does not add a replica before measuring a queue. The evidence row uses target concurrency 8 and keeps first-audio median and p90, total time, stalls, failures, memory, output quality and raw repeats; interruption tests also keep the Chapter 12 listener clocks. The closing map revisits configuration and binding (Chapters 1–3), waiting rules, data and queues (4–6), memory and measurement (7–8), and optimization and model strategies (9–12).

Code references in this chapter pin to `sglang-omni origin/main@9725235249df851281d4dc62a04b2d34b02ac0fe`. The chapter reads source, shipped configs and public measurements; it does not run a model or benchmark.

<details class="i18n-zh">
<summary>本章说法的出处</summary>

第 1 步数随仓库发布的启动形态。纯文字模式把六个 stage 放在一个 `pipeline` 进程和一张 GPU 上，仍接受文字、图像、声音或视频输入（`sglang_omni/models/qwen3_omni/config.py:136-147,257-265,412-422`；`docs/cookbook/qwen3_omni.md:46-57,206-208`）。默认语音有七个 stage，各住一个进程：image encoder、audio encoder、thinker 和 code2wav 使用 GPU 0，talker 使用 GPU 1，preprocessing 和 decode 是 CPU stage（`config.py:268-318,425-452`）。这些数量不含 HTTP server 和 coordinator。

第 2 步区分服务器模式和请求输出。两种模式都接受多模态输入（`docs/cookbook/qwen3_omni.md:206-208`）。纯文字在 `mm_aggregate` 汇合实际输入分支；语音部署由 thinker 自己汇合（`sglang_omni/models/qwen3_omni/config.py:136-189,212-254`）。语音请求使用 `modalities: ["text"]` 时以 decode 为终点并排除 talker；加入 `"audio"` 后也以 code2wav 为终点（`sglang_omni/models/qwen3_omni/request_builders.py:200-261`；`tests/unit_test/qwen3_omni/test_pipeline.py:898-930,1935-1947`）。公开请求默认只输出文字；向纯文字服务器请求声音也不会返回声音（`docs/basic_usage/omni.md:22,154-170,199-200,359,386-395`）。

第 3 步保留第 8 章第 1 步的 PR #1235 公开拓扑：H200、thinker TP2，code2wav 在其中一个 thinker GPU 上。8 路并发时，只把 talker 从同一张 GPU 移到第三张卡，两次 p90 首音的均值从 2.680 秒降至 1.439 秒，约 46%。精确原始值来自 PR #1235；固定版本 tuning 指南给出四舍五入范围，以及单请求比较：独占改善首音，却让端到端延迟增加 14–17%（`docs/cookbook/qwen3_omni/tuning.md:52-69`）。第 8 步的 TP1 方案拓扑不同，需要自己的比较。

第 4 步从 H100 BF16 同卡配置 的 `2 + 2 + 78 + 10 + 2 = 94%` 开始（`examples/configs/qwen3_omni_colocated_h100_bf16.yaml:1-20`）。thinker 工厂默认 `encoder_mem_reserve` 为 0.05。没有显式 `thinker.engine.mem_fraction_static` 时，先减去整卡的 5 个百分点再推导 AR 预算，所以有效 AR 比例是 `0.78 − 0.05 = 0.73`；这份预留是 thinker AR 之外的 encoder 工作余量，不是另外两个 encoder stage 的 2% + 2%（`sglang_omni/models/qwen3_omni/stages.py:155-215,1230-1243,1358-1373`；`sglang_omni/scheduling/sglang_backend/server_args_builder.py:176-210`）。显式匹配时跳过预留，冲突时拒绝，按字节申报 KV 时跳过比例调整（`tests/unit_test/qwen3_omni/test_sglang_ar_budget.py:491-511,540-562`；`stages.py:1384-1402`）。同卡要求五个 GPU stage 共用一卡、TP 为 1、worker 内不复制进程，并且每个 GPU stage 都申报预算（`sglang_omni/models/qwen3_omni/placement.py:55-60,84-108,122-187`）。这些是配置算式与校验规则，不是实测占用。

第 5 步对照 BF16、FP8 和 INT4。兼容矩阵允许三种精度用于纯文字输出、thinker/talker 分卡的 TP1 或 TP2，以及同卡 TP1（`docs/cookbook/qwen3_omni.md:25-44`）。BF16 是默认值。FP8 checkpoint 为 thinker 和 talker AR 提供精度配置，`--dtype fp8` 不是选择机制（`docs/cookbook/qwen3_omni.md:153-169`；`sglang_omni/models/weight_loader.py:19-42`）。INT4 checkpoint 把 thinker 权重按每 128 个一组存成 4 bit，talker AR 和 code2wav 仍是 BF16（`docs/cookbook/qwen3_omni.md:181-195`）。教程文档在 INT4 行明确写出 code2wav 使用 BF16；实现也在其他行省略 code2wav `dtype` 时默认使用 BF16（`sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:146-154,1230-1260`；`sglang_omni/models/weight_loader.py:19-26`）。约 60、40、30 GB 及 50%/25% 降幅出现在单卡 H100/H20 章节，但具体数量是权重本身、加载的 stages、运行峰值还是整个服务器并不明确。它们不是实测单卡预算，也不是本地显存、延迟或质量实测（`docs/cookbook/qwen3_omni.md:196-200`）。

第 6 步应用随仓库发布的 replica2 config。thinker 默认最多运行 64 个请求，每个 talker engine 默认 32 个（`sglang_omni/models/qwen3_omni/stages.py:1276-1286`；`sglang_omni/models/qwen3_omni/config.py:37,454-496`）。两个 talker 副本让每个 code2wav 进程计算 `codec_state_slots = 32 × 2 = 64`，各自建立独立状态池，覆盖 talker 可运行的流（`config.py:468-476`；`tests/unit_test/qwen3_omni/test_colocation_config.py:177-203`；`sglang_omni/models/qwen3_omni/components/code2wav_scheduler.py:1284-1299`）。状态池满了会退回看左侧上下文的无状态解码，不会拒绝请求（`code2wav_scheduler.py:296-314`）。config 把 talker/code2wav 副本 0 放在 GPU 1，副本 1 放在 GPU 2，每个副本 GPU 申报 `12.3% + 1.4% = 13.7%`（`examples/configs/qwen3_omni_speech_replica2.yaml:1-42`）。这是每个进程的配置容量，不是全部署共享一个池，不是吞吐实测；自定义副本策略下也不是绑定契约保证。

第 7 步区分健康与性能。readiness 发送一张小图、一秒声音和一条短指令，每个生成 token 的 stage 最多生成 8 个新 token（`docs/cookbook/qwen3_omni.md:202-204`；`sglang_omni/models/qwen3_omni/config.py:328-366`）。视频、大 batch 和其他输入大小可能仍会在之后预热（`docs/basic_usage/omni.md:345-349`）。比较先解析配置，再固定输入、采样、硬件和预热，只改一个部署选择（`docs/basic_usage/process_topology.md:52-53`；第 8 章第 6、8 步）。文档中的 `--concurrencies 1,16 --repeats 5 --generate-only` 给每组十次测量；原始重复、失败和显存也进入比较。首音和服务器时间与听者卡顿、第 12 章停答／回应时钟分开。benchmark 说明 p99 需要底层队列里至少 100 个测量请求，不是只看运行次数（`benchmarks/README.md:249-288`；`benchmarks/eval/benchmark_omni_seedtts.py:504-505,552-561`）。

第 8 步为 8 路并发语音请求构造一个 TP1 起步假设：默认 BF16 语音、文字和声音输出、输入 encoders、thinker 和 code2wav 在 GPU 0、talker 独占 GPU 1。这个假设来自第 3 步不同的 H200/TP2 证据，仍需本地 A/B 比较。8 小于 talker 的 32 请求上限，还剩 `32 − 8 = 24` 个未占上限，所以算例不在测量排队前增加副本。证据行使用目标并发 8，保留首音中位数和 p90、总耗时、卡顿、失败、显存、输出质量和原始重复；打断测试还保留第 12 章听者时钟。收尾地图回看配置与绑定（第 1–3 章）、等待规则、数据与队列（第 4–6 章）、显存与测量（第 7–8 章）、优化与模型策略（第 9–12 章）。
