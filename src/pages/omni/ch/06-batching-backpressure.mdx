<summary>Where this chapter's claims come from</summary>

Step 1 constructs a `SimpleScheduler` collection example with four batch slots. A and B are queued at 0 ms; C arrives at 6 ms. With `max_batch_wait_ms=0`, the scheduler takes A and B without waiting for the two empty slots. In the counterfactual five-ms panel, the collection deadline expires at 5 ms, before C arrives, so A and B enter compute five ms later. The animation plays the zero-delay start, the five-ms deadline and start, then C's late arrival. The timelines omit compute time and every other delay. The five-ms budget is not a shipped MiniCPM-o default or a recommendation.

Step 2 constructs two running rows. A and B occupy both rows in round 1, so C waits. A finishes after that round; B remains in `running_batch`, and C can take the free row if token memory also permits. The animation shows A's grey finished card, C's refill, then B and C advancing together. The two-row cap is a teaching device. MiniCPM-o's talker factory currently passes `max_running_requests=32`, which this small figure does not depict. `generation_batch_policy.py` builds and validates server arguments; `OmniScheduler` owns `waiting_queue`, `running_batch` and admission. Optional prefill coalescing is outside this step.

Step 3 constructs a batch-capable `ReferenceEncodeService` with cap four and zero delay. A, B and C are ready, so non-blocking collection takes all three and leaves one slot empty. D arrives afterward and belongs to the next collection. The shipped defaults remain cap one and zero delay; a larger cap enables this path only when `hook.can_encode_batch()` also succeeds. One batch call returns separate outcomes to the three requests. The animation drains the queue, runs the call, returns the results, then lets D arrive.

Step 4 uses MiniCPM-o's real audio-encoder configuration: request cap eight, zero collection delay and 24,000 charged mel frames. The teaching requests cost five, two and two full 3,000-frame windows. A and B fit at 21,000 frames; adding C would reach 27,000, so `SimpleScheduler` puts C back at the head of `pending_messages` even though three requests are below the count cap. Both panels use the same origin and 27,000-frame scale, with the 24,000-frame limit at the same position. The animation holds C in pending, reveals the 27,000-frame trial, then returns the outlined C with `appendleft()` without changing the scale. The real budget admits eight full 30-second chunks. These teaching costs are not benchmark observations, and the budget is not a precise FLOP or memory measurement.

Step 5 separates two implementations. MiniCPM-o Code2Wav returns a `SimpleScheduler` with cap 16, zero delay and `batch_wait_when_idle=false`; it collects complete requests and calls `vocode_and_release([A, B])`. Optional `StreamingVocoderBase` subclasses instead ingest each `stream_chunk` into request-local state, select ready participants and call `run_step([A, B])`. Both preserve per-request outputs, but these are not the same message path. The animation plays the left collection and call, then the right ingest, selection and shared step. Plan construction has no separate stage card. The two-request, one-call construction is not a latency or throughput claim.

Step 6 quotes, rather than reruns, the historical H200 FIFO comparison in `batch.md` and PR #2271. With 200 SeedTTS EN requests, client concurrency 16, zero delay, 50 excluded warmups and three mixed-reference repeats, B1 and B8 averaged 4.100 and 5.652 requests/s. The derived improvement is 37.9% relative to B1. The bars replay the two quoted averages on one axis before showing that calculation; they do not simulate a new request trace. This belongs to historical code `89e60d0bf216bacd0e072d79f969550469614662` and its controlled environment. It is not a current-main benchmark or a universal optimum; current MiniCPM-o Code2Wav has cap 16 and a changed implementation.

Step 7 constructs two independent admission examples with cap two and active A and B. At the router, C cannot acquire a permit, so `RouterOverloaded` becomes HTTP 429 before worker dispatch. At the coordinator, two requests already meet `max_in_flight`, so C raises `QueueFullError` before pipeline submit and the OpenAI error mapping returns HTTP 503. Router permits and worker-load guards remain held through response EOF, upstream error or downstream cancellation. The animation plays the router failure and 429 before the independent coordinator failure and 503. These teaching caps are not deployment defaults, and the two status codes belong to different boundaries.

Step 8 constructs three HTTP body frames, with frame one delivered and two upstream. While the body is active, each downstream `DirectResponseBody.poll_frame()` invokes the inner `reqwest::Body` poll once and returns `Pending`, one data frame, EOF or an error. The animation plays one downstream poll, one upstream poll, frame two's return, and delivery; the final counts are two delivered and one upstream. The adapter adds no body pump, application queue or extra relay task, and releases its request lease on termination. Zero adapter-owned queues does not eliminate socket, HTTP-runtime or worker buffering. This response-relay path is separate from classified-upload buffering and worker-stage queues.

<summary>本章说法的出处</summary>

第 1 步构造一个四格 `SimpleScheduler` 收集例子。A、B 在 0 ms 已入队，C 在 6 ms 才到。`max_batch_wait_ms=0` 时，scheduler 直接拿走 A、B，不等另外两个空位。在对照的 5 ms 面板里，收集截止时间是 5 ms，仍早于 C 到达，因此 A、B 晚 5 ms 进入计算。动画依次播放零等待启动、5 ms 到期启动和 C 晚到。时间线不画计算耗时和其他等待。5 ms 不是 MiniCPM-o 的出厂默认值，也不是推荐配置。

第 2 步构造两行 running batch。第 1 轮 A、B 占满两行，C 等待。该轮后 A 结束，B 继续留在 `running_batch`；token 显存也允许时，C 补进空行。动画依次显示灰色 A 结束卡、C 补位，以及 B、C 一起前进。两行上限只是教学构造。MiniCPM-o talker 工厂当前传入 `max_running_requests=32`，这张小图没有描绘 32 行。`generation_batch_policy.py` 构造并校验 server args；`OmniScheduler` 持有 `waiting_queue`、`running_batch` 并执行准入。可选的 prefill 凑批不在本步展开。

第 3 步构造一个支持批处理的 `ReferenceEncodeService`，上限为 4，等待为 0。A、B、C 已就绪，非阻塞收集一次带走三条，留下一个空位。D 随后才到，属于下一次收集。出厂默认值仍是上限 1、等待 0；只有 `hook.can_encode_batch()` 也通过，调大上限才会启用这条路径。一次批量调用把三份结果分别交还三条请求。动画依次排空队列、执行调用、返回结果，再让 D 到达。

第 4 步使用 MiniCPM-o audio encoder 的真实配置：请求上限 8、零收集等待、24000 个计费 mel 帧。教学请求分别计 5、2、2 个完整的 3000 帧窗口。A、B 合计 21000 帧，可以同批；再加 C 会达到 27000 帧，因此即使三条低于请求数上限，`SimpleScheduler` 仍把 C 放回 `pending_messages` 队首。两幅图从同一原点起，共用 0–27000 帧比例尺，24000 帧上限也在同一位置。动画先让 C 等待，再显示 27000 帧试算，最后把虚线 C 用 `appendleft()` 放回队首，比例尺不变。真实预算可容纳八段完整的 30 秒音频。这些教学成本不是实测结果，预算也不是精确的 FLOP 或显存测量。

第 5 步分开两种实现。MiniCPM-o Code2Wav 返回 `SimpleScheduler`，上限 16、零等待、`batch_wait_when_idle=false`；它收集完整请求并调用 `vocode_and_release([A, B])`。可选的 `StreamingVocoderBase` 子类则把每个 `stream_chunk` ingest 到请求自己的状态，选择就绪参与者，再调用 `run_step([A, B])`。两边都保留各请求输出，但不是同一条消息路径。动画先播放左侧收集和调用，再播放右侧 ingest、选择和合步。构造计划没有单独的舞台卡片。两条请求、一次调用的构造不是延迟或吞吐结论。

第 6 步引用而非重跑 `batch.md` 和 PR #2271 的历史 H200 FIFO 对照。在 SeedTTS EN 前 200 条、客户端并发 16、零等待、剔除 50 条预热、混合参考音频重复三次的条件下，B1 与 B8 平均吞吐为 4.100 和 5.652 requests/s。相对 B1 的派生提升为 37.9%。两根柱先在同尺上重现两个历史平均值，再显示这道算式，并不模拟新的请求轨迹。结果属于历史代码 `89e60d0bf216bacd0e072d79f969550469614662` 和当时的受控环境，不是当前主线 benchmark 或普遍最优结论；当前 MiniCPM-o Code2Wav 上限为 16，实现也已改变。

第 7 步构造两个独立准入例子，上限都是 2，A、B 仍在处理。Router 中 C 获取不到许可，`RouterOverloaded` 在发往 worker 前映射为 HTTP 429。Coordinator 中两条请求已经达到 `max_in_flight`，C 在 pipeline submit 前抛出 `QueueFullError`，OpenAI 错误映射返回 HTTP 503。Router 许可和 worker load guard 持有到响应 EOF、上游错误或下游取消。动画先播放 router 拒绝和 429，再播放独立的 coordinator 拒绝和 503。教学上限不是部署默认值，两个状态码属于不同边界。

第 8 步构造三个 HTTP body 数据帧，第 1 帧已交付，两帧仍在上游。传输未结束时，下游每次调用 `DirectResponseBody.poll_frame()`，adapter 就调用一次内部 `reqwest::Body` 的 poll，并返回 `Pending`、一个数据帧、EOF 或错误。动画依次播放一次下游 poll、一次上游 poll、第 2 帧返回和交付，末态为交付 2 帧、上游 1 帧。它不增加 body pump、应用队列或额外 relay task，并在终止时释放 request lease。adapter 自己的队列是 0，不代表 socket、HTTP 运行时或 worker 没有缓冲。这条响应转发路径与分类上传缓冲、worker 内部队列分开。
