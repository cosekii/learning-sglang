<summary>本章说法的出处</summary>

第 1 步依据默认的三个 stage 路线，见 `sglang_omni/models/fishaudio_s2_pro/config.py:23-67` 和 `stages.py:522-552`。首个非最后的流式窗口在 40 帧打开（`streaming_vocoder.py:43-66`；`scheduling/audio_stream.py:86-102`）。不足 40 帧就结束的请求仍会通过最后一次 flush 解码（`scheduling/audio_stream.py:106-148`）。每个生成帧带一个语义 code 和其余九个 codes 给 vocoder，所以构造算式是 40 × 10 = 400 个从 codebook 选出的 code（`sglang_model.py:418-510`；`payload_types.py:35-50`）。一个 codec 帧在 44,100 Hz 下代表 2,048 个采样点（`fish_speech/configs/modded_dac_vq.yaml:3-29`；`fish_speech/models/dac/modded_dac.py:885-913,928-988`）。得到的 1.858 秒是声音时长，不是实际等待。

第 2 步依据 `sglang_omni/models/fishaudio_s2_pro/stages.py:249-376,425-490`：参考声音先变单声道，重采样到 44,100 Hz，再进入参考 DAC。构造算例从 16 kHz 的 1 秒声音开始。DAC 每帧 2,048 个采样点，所以 `ceil(44,100 ÷ 2,048) = 22` 帧，需要补 956 个采样点，输出共十行。`scheduling/reference_encoder.py:344-413` 在 CPU 缓存相同参考声音的 codes 并返回副本；这不是 AR KV。已有 `vq_codes` 可以跳过编码，没有参考声音的请求会省略这段声音提示。

第 3 步依据 `sglang_omni/models/fishaudio_s2_pro/tokenizer.py:53-73,94-162` 和 `model_runner.py:288-356`。Slow AR 是沿时间轴走的外层循环。目标文字使用普通 tokens。每个参考帧由 code 0 形成一个语义 token，同时十行 codes 都会改变这个位置的模型输入。精确的 embedding 平均是 `(文字 embedding + 十个 codec embeddings) ÷ sqrt(11)`，见 `fish_speech/models/text2semantic/audio_decoder.py:597-612`。多个参考声音沿时间拼接；没有参考声音时会省略 system 声音块。

第 4 步跟随一个非结束帧，见 `sglang_omni/models/fishaudio_s2_pro/sglang_model.py:294-300,418-510`。Fast AR 是内层循环。第 0 次调用接收投影后的 Slow 隐藏状态，不提供 vocoder code。第 1–9 次调用通过 argmax 选出其余九个 codes。engine 保存 Slow 原始 `semantic_token` 和由它得到的 `sem_id`（code 0），再保存这九个 codes，共 11 行。`streaming_vocoder.py:88-106` 去掉原始 token，把其余十行送入 vocoder。1+9=10 次 Fast 调用，code 9 之后没有第 11 次调用。

第 5 步依据 `model_runner.py:62-100,148-191` 和 `sglang_model.py:365-382,484-488`。上一帧的原始 token 和全部十个 DAC codes 会进入下一次 Slow 输入。Slow KV 通过 SGLang 保留 prompt 和之前的帧，`model_runner.py:324-344` 实际处理 `req.prefix_len`。`request_builders.py:65-78,160-168` 让 `extra_key` 对全部十行参考 codes 做指纹，避免不同参考声音仅因 code 0 相同就共享 radix KV。参考声音相同、共同前缀仍在 cache 里时，目标后缀不同也能复用这段前缀；匹配不保证缓存仍命中。Fast KV 只覆盖一帧内的 0–9 位置，在下一次 Slow 输出前重置（`fish_speech/models/text2semantic/audio_decoder.py:394-411,505-526,547-595`）。第 2 步的参考 code 缓存是另一种 CPU 成品缓存。

第 6 步依据 `model_runner.py:48-76` 和 `request_builders.py:148-167,192-202,233-248`。EOS 是 `<|im_end|>`：Fast AR 仍会为这次 Slow 输出运行，但收集器丢掉结束帧，保留之前接受的帧。立即遇到 EOS 会留下零个音频 codes，随后报错，不返回空声音。长度用尽会保留接受的帧，并写 `finish_reason="length"`。有效上限是 `min(请求上限, 2048, max(4096−1−prompt tokens,1))`，请求默认上限是 1,024（`payload_types.py:35-50`）。中止会清掉流状态，拦截待送 chunks 和最终成功输出，但不能收回已经交付的 chunks。

第 7 步用构造的 90 帧流走过 `scheduling/audio_stream.py:65-148,151-239,242-333`。默认规则在 40 帧开窗，后续读取 20 帧旧内容和最多 45 帧新内容，并保留 512 个采样点的声音尾巴做交叉混合。三次调用因此分别读取 40、65、25 帧。输出采样点合计是 `90 × 2,048`。每个未结束调用都留下新的 512 采样点尾巴；下一次交叉混合旧尾巴并留下自己的，最后一次释放最后的尾巴。旧帧和声音尾巴用于连接窗口，不是 Qwen 式保留神经 codec 状态。`request_builders.py:276-298` 和 `scheduling/audio_vocoder.py:116-182` 在已有流式声音后不会再解码整个请求。

第 8 步依据 `scheduling/audio_vocoder.py:194-224` 和 `scheduling/streaming_simple_scheduler.py:311-390,434-480`。非流式请求先完成 Dual-AR，再合并 `[11,T]` 结果。vocoder 去掉原始行，补到最长请求的长度，再把每份输出裁回自己的长度。两个构造请求有 90 和 40 帧，所以补位后的调用是 `[2,10,90]`，请求 B 有 50 帧补位。默认收集器最多合并八个已完成请求，额外请求最多等待 2 ms。第 7 步的流式 chunks 仍逐请求运行。交付调度不改变 Dual-AR 选择。章末 session 问题由第 12 章回答。
