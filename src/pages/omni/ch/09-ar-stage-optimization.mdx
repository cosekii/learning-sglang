<summary>Where this chapter's claims come from</summary>

Step 1 constructs three prompts that reuse one reference voice. The roughly 250 ms reference encode comes from the public MOSS-TTS-Local-v1.5 profile in `Awesome-ML-SYS-Tutorial/sglang/sglang-omni/moss-tts-local-v15-blog-zh.md:54-58`; it is not a local measurement or a universal encoder latency. The current encoder hook produces reference codes in `sglang_omni/models/moss_tts/reference_encoder.py:110-143`. The four map entries are the mechanisms explained by the following steps.

Step 2 follows `sglang_omni/scheduling/reference_encoder.py:24-35,84-119,344-413` and `sglang_omni/models/moss_tts/reference_encoder.py:74-105`. The full key covers model version, encoder settings, result type, audio content and encode choices, not the prompt text. One constructed miss and two hits reduce GPU encode work from three passes to one. The 500 ms difference uses Step 1's approximate profile and is not an end-to-end latency result. Loads return copies of the stored tensor.

Step 3 follows `sglang_omni/scheduling/reference_encoder.py:361-413`. With no cached entry, A creates an in-flight future; B and C join it, then load copies after A finishes. Later matching requests can hit the stored entry. The independent-call comparison turns batching off. MOSS also deduplicates identical identifiers inside its own batch encoder (`sglang_omni/models/moss_tts/reference_encoder.py:113-143`), so this step isolates the generic single-flight rule rather than attributing every deduplication to it.

Step 4 follows `sglang_omni/model_runner/base.py:502-605` and `sglang_omni/scheduling/omni_scheduler.py:5125-5197`. Launch queues GPU work and records an event without waiting; resolve collects the previous step's token or frame and emits it downstream. GPU stream order still preserves the N−1 → N model dependency, and an unfinished event requires synchronization. The diagram shows ordering only and assigns no saved time. MOSS-TTS-Local resolves from a device snapshot, defaults async decode off (`sglang_omni/models/moss_tts_local/stages.py:326-346`), and reports neutral public measurements in `Awesome-ML-SYS-Tutorial/sglang/sglang-omni/moss-tts-local-v15-blog-zh.md:210-216`.

Step 5 follows `sglang_omni/models/qwen3_omni/components/audio_layer_graph.py:163-221` and `sglang_omni/models/qwen3_omni/components/audio_encoder.py:170-268`. The graph records the audio layer stack, not one kernel or the whole request. Matching calls replay that stack while input copies and metadata updates remain outside it. The option defaults off. Capture failure or a nonmatching input falls back to the original eager layers; no timing win is claimed.

Step 6 follows `sglang_omni/models/qwen3_omni/components/audio_layer_graph.py:22-23,223-275`. The default buckets are 128 through 4096 tokens. The constructed 300-token example selects 512, adds 212 zero positions and returns `output[:300]`. Real and padded positions are processed apart, so real outputs cannot read padding. Selection also checks that both groups fit the captured layout; unavailable or nonmatching graphs fall back to eager execution. These numbers describe tensor shape, not a timing result.

Step 7 summarizes Steps 1–6 without adding a performance claim or implying that one model combines every mechanism. Steps 1–4 use MOSS-TTS and the generic reference service; Steps 5–6 use Qwen3-Omni's audio encoder. The closing hand-off follows Learning SGLang Ch. 20 Steps 1–3: ten Qwen codec frames represent 800 ms of sound, and the next chunk must arrive before the current one ends. The 80 ms per frame is playback duration, not vocoder compute time. Chapter 10 will examine cross-request batching, retained codec state and vocoder CUDA graphs against that deadline.

Code references in this chapter pin to `sglang-omni origin/main@3a31bd72e034db37ce5115a03dd4827b449683be`. The chapter reads source and public results; it does not run a model or benchmark.

<summary>本章说法的出处</summary>

第 1 步构造三个共用一段参考音频的 prompt。约 250 ms 的参考编码耗时来自公开 MOSS-TTS-Local-v1.5 profile，见 `Awesome-ML-SYS-Tutorial/sglang/sglang-omni/moss-tts-local-v15-blog-zh.md:54-58`。它不是本机实测，也不是所有编码器的固定耗时。当前 encoder hook 在 `sglang_omni/models/moss_tts/reference_encoder.py:110-143` 生成参考 codes。地图的四项由后续步骤分别解释。

第 2 步依据 `sglang_omni/scheduling/reference_encoder.py:24-35,84-119,344-413` 和 `sglang_omni/models/moss_tts/reference_encoder.py:74-105`。完整 key 覆盖模型版本、encoder 设置、结果类型、音频内容和 encode choices，不含 prompt 文本。构造的一次 miss 和两次 hit 把 GPU encode 从三次减为一次。500 ms 差额沿用第 1 步的约数，不是端到端延迟结果。每次读取返回已存 tensor 的副本。

第 3 步依据 `sglang_omni/scheduling/reference_encoder.py:361-413`。没有缓存项时，A 创建 in-flight future，B、C 加入它，等 A 完成后读取副本。后来的相同请求可以命中已存条目。独立调用对照关闭了 batching。MOSS 也会在自己的 batch encoder 内合并相同标识（`sglang_omni/models/moss_tts/reference_encoder.py:113-143`），所以本步只隔离通用 single-flight 规则，不把所有去重都归给它。

第 4 步依据 `sglang_omni/model_runner/base.py:502-605` 和 `sglang_omni/scheduling/omni_scheduler.py:5125-5197`。launch 让 GPU 工作排队并记录 event，不等待 GPU；resolve 收集上一步的 token 或 frame 并发往下游。GPU stream 仍保持 N−1 → N 的模型依赖，event 未完成时仍要同步等待。图中只有顺序，没有填写节省时间。MOSS-TTS-Local 从 device 快照 resolve，默认关闭异步 decode（`sglang_omni/models/moss_tts_local/stages.py:326-346`），公开测量为性能中性，见 `Awesome-ML-SYS-Tutorial/sglang/sglang-omni/moss-tts-local-v15-blog-zh.md:210-216`。

第 5 步依据 `sglang_omni/models/qwen3_omni/components/audio_layer_graph.py:163-221` 和 `sglang_omni/models/qwen3_omni/components/audio_encoder.py:170-268`。graph 录制 audio 层序列，不等于一个 kernel，也不覆盖整个请求。匹配调用重放层序列，输入拷贝和 metadata 更新仍在外面。该选项默认关闭。capture 失败或输入不匹配会回退到原来的 eager 层；本步不声称耗时收益。

第 6 步依据 `sglang_omni/models/qwen3_omni/components/audio_layer_graph.py:22-23,223-275`。默认 bucket 从 128 到 4096 token。构造的 300-token 输入选择 512，补 212 个零位置，再返回 `output[:300]`。真实和补零位置分开处理，真实输出读不到 padding。选择时还检查两组位置能否装进已 capture 的布局；没有可用或匹配的 graph 就回退 eager。这些数字描述 tensor 形状，不是耗时结果。

第 7 步总结第 1–6 步，不新增性能声明，也不暗示一个模型同时使用所有机制。第 1–4 步使用 MOSS-TTS 和通用 reference service，第 5–6 步使用 Qwen3-Omni 的 audio encoder。交接依据 Learning SGLang 第 20 章第 1–3 步：十个 Qwen codec frames 代表 800 ms 声音，下一段必须在当前段播完前到达。每帧 80 ms 是播放时长，不是 vocoder 计算耗时。第 10 章将在这条期限线上检查跨请求 batching、保留的 codec 状态和 vocoder CUDA graph。
