## 第 1 步 · 两种步有了名字

> **一句话：** 第 3 章的第一次前向叫 **prefill**，之后每一次前向叫 **decode**。

### 图上是什么

- 上面一行 token：蓝色 5 个是 prompt（`The`、`␣capital`、`␣of`、`␣France`、`␣is`），橙色 2 个是模型补上的 `␣Paris`、`.`（第 1 章）。
- 下面一行步骤：蓝色长条「第 1 步 · prefill」盖住 5 个 prompt token，标注「5 个 token，一次前向，填满 cache」。
- 两个橙色小块「第 2 步」「第 3 步」，都写着 decode；旁边标签「每步 1 个 token，读取 cache」。

### 两种步对照

| | prefill | decode |
|---|---|---|
| 一步输入几个 token | prompt 全部（这里 5 个） | 1 个（上一步生成的） |
| 写 KV cache | 每个 prompt token 一个槽位 | 1 个槽位 |
| 读 KV cache | 不读 | 读全部已存的 k、v |
| 第 3 章哪几步 | 第 2–3 步 | 第 4–7 步 |

### SGLang 里叫什么

SGLang 源码里 prefill 叫 **extend**：`ForwardMode.EXTEND`，注释写着「通常也叫 prefill」。叫 extend 是因为序列开头的 cache 可能已经算好（第 8 章的 prefix caching），这一步只把剩下的部分接上去。decode 就叫 `ForwardMode.DECODE`。本书用 prefill 和 decode 这两个通用叫法。

第 2–4 步把一步拆开，看 GPU 上是什么在花时间。

## 第 2 步 · 每一步都要把 16 GB 权重读一遍

> **一句话：** 一次前向要用到模型的每个矩阵，它们都要从 HBM 运进计算单元；8B 模型是 16 GB，和这一步有几个 token 无关。

### 图上是什么

- 左框「内存（HBM）」：GPU 的主内存，里面蓝色的「权重 16 GB」在闪。
- 中框「计算」：做乘法的单元，写着 `5 × 16 GFLOP = 80 GFLOP`（第 3 步讲）。
- 两框之间的粗箭头在流动，上写「读取 16 GB」，下写「每一步」。
- 右边 5 个 `tok` 小块：这一步的输入 token。
- 底部灰色脚注：16 GB 是全部参数；其中 1 GB 的 embedding 表只查表，所以实际读约 15 GB。

### 公式

$$
M_W = \text{参数个数} \times b = 8 \times 10^9 \times 2\ \text{B} = 16\ \text{GB}
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $M_W$ | 一步要从 HBM 读出的权重字节数 | 16 GB | 本步；`src/numbers.ts` 的 `W_GB` |
| $b$ | 每个数的字节数（bf16） | 2 B | 第 3 章第 9 步；`BYTES` |

HBM（High Bandwidth Memory）是 GPU 上的大容量内存，H100 有 80 GB。计算单元旁边的片上存储只有几十 MB，放不下 16 GB，所以每次前向都得把每个矩阵（第 2 章第 3 步的 $W_Q, W_K, W_V$ 和其余所有矩阵）重新从 HBM 读一遍。

### 代入图上的数：脚注的 15 GB

| 量 | 计算 | 结果 |
|---|---|---|
| embedding 表 | 128,256 行 × 4,096 个数 × 2 B | 1.05 GB |
| 一步实际流过的权重 | 16 − 1.05 | 约 15 GB |

embedding 表把 token id 变成第 2 章第 2 步的 $x$，一步只取自己那几个 token 的行，不需要整张表。本书仍按 16 GB 算，第 8 步说明这个取整几乎不影响结论。

## 第 3 步 · prefill：五个 token 共用一次读取

> **一句话：** 一个权重从 HBM 运来一次，在计算单元里和 5 个 token 的向量都乘掉；读的字节不变，计算量是 5 倍。

### 图上是什么

- 右边 5 个蓝色 `tok` 小块在闪，标题「5 个 token 输入」，从右往左的箭头在流动。
- 计算框：`5 × 16 GFLOP = 80 GFLOP`。
- 读取箭头仍是「读取 16 GB」。

### 公式

$$
\text{计算量} = n \times f
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $n$ | 这一步输入的 token 数 | 这里 5 | 本步 |
| $f$ | 一个 token 过一遍模型的运算次数 | 16 GFLOP | `src/numbers.ts` 的 `GFLOP_PER_TOKEN` |

注意：第 3 章第 10 步用 $n$ 表示序列当前的长度。本章 $n$ 指**一步里的 token 数**，序列长度另记为 $c$（第 6 步）。

GFLOP = 十亿次浮点运算。$f$ 怎么来：矩阵乘向量时，每个权重做一次乘法、一次加法，8B 个参数就是 $2 \times 8 \times 10^9 = 16 \times 10^9$ 次。attention 里 query 和 key 的点积（第 2 章第 4 步）不在这 16 GFLOP 里，它和矩阵乘法比很小。

### 代入图上的数

$$
5 \times 16\ \text{GFLOP} = 80\ \text{GFLOP}
$$

读取仍是 $M_W = 16$ GB。按每读 1 字节做几次运算算：$80\ \text{GFLOP} / 16\ \text{GB} = 5$ 次/字节。

### 为什么能并行

五个 token 的矩阵乘法互不依赖：它们乘的是同一组权重，各自的向量不同。attention 里的前后依赖由第 2 章第 7 步的 causal 三角形处理，也在同一次前向里算完。

第 4 步换成 decode，只有 1 个 token。

## 第 4 步 · decode：同样的读取，一个 token 的计算

> **一句话：** decode 的 $n = 1$；为了这一个 token，16 GB 照样全读一遍，计算只有 16 GFLOP。

### 图上是什么

- 右边只剩 1 个橙色 `tok`，标题「1 个 token 输入」。橙色和第 1 步的 decode 块同色。
- 计算框：`1 × 16 GFLOP = 16 GFLOP`。
- 读取箭头：「读取 16 GB」，没变。

### 代入图上的数

| | prefill（第 3 步） | decode（本步） |
|---|---|---|
| $n$ | 5 | 1 |
| 计算 $n \times f$ | 80 GFLOP | 16 GFLOP |
| 读取 $M_W$ | 16 GB | 16 GB |
| 每字节运算次数 | 5 | 1 |

一个 token 的向量要乘过每一个矩阵，少了任何一个都算不出输出，所以 decode 不能只读一部分权重。

### 接下来

第 5 步把字节和运算次数换算成时间。

## 第 5 步 · 换算成时间：读 4.8 ms，算 0.016 ms

> **一句话：** 在 H100 上读 16 GB 要 4.8 ms，一个 token 的计算只要 0.016 ms；一步取较慢的那个，计算单元 99.7% 的时间在等。

### 图上是什么

- 「每步耗时」两根条：青色「内存」4.8 ms，蓝色「计算」0.016 ms（短到几乎看不见）。
- 说明行：「步耗时 ≈ 4.8 ms，等待内存」。
- 计算框里的忙碌条：几乎全空，一小截红色，下写「忙碌占这一步的 0.3%」。
- 脚注：3.35 TB/s 和 989 TFLOP/s 是 H100 SXM 的标称峰值，实际达不到。

### 公式

$$
t_{\text{mem}} = \frac{M_W}{BW},\qquad
t_{\text{comp}} = \frac{n\,f}{F},\qquad
t_{\text{step}} = \max(t_{\text{mem}},\ t_{\text{comp}})
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $M_W$ | 权重字节数 | 16 GB | 第 2 步 |
| $BW$ | HBM 带宽：每秒能读出的字节数 | 3.35 TB/s | `src/numbers.ts` 的 `BW` |
| $n$ | 这一步的 token 数 | 1 | 第 3 步 |
| $f$ | 每个 token 的运算次数 | 16 GFLOP | 第 3 步 |
| $F$ | 每秒能做的浮点运算次数（bf16） | 989 TFLOP/s | `src/numbers.ts` 的 `TFLOPS` |
| $t_{\text{mem}}, t_{\text{comp}}$ | 读取时间、计算时间 | | 本步 |
| $t_{\text{step}}$ | 一步的耗时 | | 本步 |

单位换算：GB ÷ TB/s 正好是 ms，GFLOP ÷ TFLOP/s 也是 ms。

### 代入图上的数

| 量 | 计算 | 结果 | 图上 |
|---|---|---|---|
| $t_{\text{mem}}$ | 16 ÷ 3.35 | 4.78 ms | 4.8 ms |
| $t_{\text{comp}}$ | 16 ÷ 989 | 0.0162 ms | 0.016 ms |
| $t_{\text{step}}$ | max(4.78, 0.0162) | 4.78 ms | 步耗时 ≈ 4.8 ms |
| 忙碌占比 $t_{\text{comp}} / t_{\text{step}}$ | 0.0162 ÷ 4.78 | 0.34% | 0.3% |

### 为什么取 max

计算单元在权重一到就开始乘，读取和计算同时进行。哪个更慢，一步就要等哪个。这里内存慢了约 300 倍。

第 6 步：decode 除了权重，还要读 KV cache。

## 第 6 步 · decode 还要读 KV cache

> **一句话：** decode 的 query 要读 cache 里所有 k、v（第 3 章第 6 步）；上下文 8k 时 cache 有 1 GB，每步多读这 1 GB。

### 图上是什么

- HBM 框里多了青色的「kv cache · 1.0 GB，8k 上下文」；框下标签「7 个 token 时是 0.9 MB（Ch. 3 Step 9）」。
- 读取箭头变成「读取 16 + 1 GB」。
- 内存条变长到 5.1 ms，说明行「步耗时 ≈ 5.1 ms，等待内存」；计算条仍是 0.016 ms，忙碌仍显示 0.3%。

### 公式

$$
M_{KV} = c \times 128\ \text{KB},\qquad
t_{\text{mem}} = \frac{M_W + M_{KV}}{BW}
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $c$ | 序列里已有的 token 数（上下文长度） | 7 或 8,192 | 本步 |
| 128 KB | 每个 token 在全部层的 k、v | | 第 3 章第 9 步；`KB_PER_TOKEN` |
| $M_{KV}$ | 这一步要读的 cache 字节数 | | 本步 |
| $M_W, BW$ | 权重字节数、HBM 带宽 | 16 GB、3.35 TB/s | 第 2 步、第 5 步 |

### 代入图上的数

| 量 | 计算 | 结果 | 图上 |
|---|---|---|---|
| $M_{KV}$，$c = 7$ | 7 × 128 KB | 896 KB | 0.9 MB |
| $M_{KV}$，$c = 8{,}192$ | 8,192 × 128 KB | 1,048,576 KB ≈ 1.05 GB | 1.0 GB |
| $t_{\text{mem}}$ | (16 + 1.05) ÷ 3.35 | 5.09 ms | 5.1 ms |
| 忙碌占比 | 0.0162 ÷ 5.09 | 0.32% | 0.3% |

没有 cache 时是 4.78 ms（第 5 步），8k 上下文让每步慢了约 0.3 ms。计算几乎不变：读 cache 时做的点积和权重乘法比很小。

### 为什么越来越慢

每生成一个 token，$c$ 加 1，cache 多 128 KB。一次回复越往后，每步读得越多。

## 第 7 步 · 2,000 个 token 的 prefill：反过来等计算

> **一句话：** $n = 2{,}000$ 时计算要 32 ms，读取还是 4.8 ms；一步等的是计算，计算单元满负荷。

### 图上是什么

- 右边 5 个蓝色小块，最后一个写 `…`，标题「2,000 个 token 输入」（图上最多画 5 块）。
- 计算框：`2,000 × 16 GFLOP = 32 TFLOP`，忙碌条全满，蓝色，「忙碌占这一步的 100%」。
- 两根条：内存 4.8 ms，计算 32 ms；说明行「步耗时 ≈ 32 ms，等待计算」。

### 代入图上的数

用第 5 步的同一组公式：

| 量 | 计算 | 结果 | 图上 |
|---|---|---|---|
| 计算量 $n f$ | 2,000 × 16 GFLOP | 32,000 GFLOP = 32 TFLOP | 32 TFLOP |
| $t_{\text{comp}}$ | 32 TFLOP ÷ 989 TFLOP/s | 32.4 ms | 32 ms |
| $t_{\text{mem}}$ | 16 ÷ 3.35 | 4.78 ms | 4.8 ms |
| $t_{\text{step}}$ | max(4.78, 32.4) | 32.4 ms | 32 ms |
| 忙碌占比 | 32.4 ÷ 32.4 | 100% | 100% |

$M_W$ 和 $n$ 无关，所以读取时间没变。计算条约是内存条的 7 倍（32.4 ÷ 4.78 ≈ 6.8）。

这次 prefill 写进 cache 的 2,000 × 128 KB = 0.26 GB 没画进条里，算上也只多约 0.08 ms。

### 两个名词

- **计算受限（compute-bound）**：$t_{\text{comp}} > t_{\text{mem}}$，一步等计算。长 prefill 属于这种。
- **内存受限（memory-bound）**：$t_{\text{mem}} > t_{\text{comp}}$，一步等读取。decode（第 5–6 步）属于这种。

### 接下来

第 8 步把 $n$ 从 1 连续变到 4,096，找两种情况的分界。

## 第 8 步 · 分界点：每步约 300 个 token

> **一句话：** 计算时间等于读取时间的地方是 $n^* = F / BW \approx 295$；低于它一步都是 4.8 ms，高于它每多一个 token 多 0.016 ms。

### 图上是什么

- 横轴「每步 token 数」1 到 4k，纵轴「每步耗时」0.01 到 100 ms，**两个轴都是对数刻度**（每格是上一格的 10 倍）。
- 青色虚线「仅内存读取」：$t_{\text{mem}} = 4.8$ ms，水平。
- 蓝色虚线「仅计算」：$t_{\text{comp}}$，从 $n = 1$ 的 0.016 ms 斜着往上。
- 黑色粗线「实际步耗时 · 取两者中较慢的」：先平后升。
- 拐点空心圆和竖虚线，上方「≈每步 300 个 token」和「989 TFLOP/s ÷ 3.35 TB/s = 295」。
- 三个实心点：橙色 decode（$n = 1$）、蓝色「prefill，5」、蓝色「prefill，2000 个 token」。
- 底部两段：「← 内存受限 · decode 在这里」「计算受限 · 长 prefill →」。

### 公式

令 $t_{\text{comp}} = t_{\text{mem}}$（不算 cache）：

$$
\frac{n^* f}{F} = \frac{M_W}{BW}
\quad\Longrightarrow\quad
n^* = \frac{F}{BW} \times \frac{M_W}{f}
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $n^*$ | 分界点：每步多少 token 时两者相等 | 约 295 | 本步 |
| $F / BW$ | 每读 1 字节的时间里，GPU 能做多少次运算 | 295 次/字节 | 第 5 步 |
| $M_W / f$ | 每次运算对应读多少权重字节 | 16 GB ÷ 16 GFLOP = 1 字节 | 第 2、3 步 |

$M_W / f = 1$ 不是巧合：每个参数 2 字节（$b = 2$），每个参数花 2 次运算（第 3 步），一除就是 1。所以对 bf16 模型，$n^*$ 就等于 $F / BW$。

### 代入图上的数

$$
n^* = \frac{989 \times 10^{12}}{3.35 \times 10^{12}} \times 1 = 295.2 \approx 300
$$

| 点 | $n$ | $t_{\text{mem}}$ | $t_{\text{comp}}$ | $t_{\text{step}}$ |
|---|---|---|---|---|
| decode | 1 | 4.78 ms | 0.016 ms | 4.78 ms |
| prefill，5 | 5 | 4.78 ms | 0.081 ms | 4.78 ms |
| 拐点 | 295 | 4.78 ms | 4.78 ms | 4.78 ms |
| prefill，2000 | 2,000 | 4.78 ms | 32.4 ms | 32.4 ms |

decode 和 5 个 token 的 prefill 落在同一条水平线上：耗时一样。

### 和正文「把账算一次」的对应

正文用 $P$ 表示参数个数，权重字节是 $2P$，就是这里的 $M_W$；它的 $P$ 和第 1 章的 prompt 长度 $P$ 不是一回事。正文还说明：只读 15 GB 权重、输出层只在最后一个位置算，会让读取和计算一起变小，分界点几乎不动。

第 9 步看用户在聊天里感受到的是哪一段。

## 第 9 步 · 聊天里的两段：首字等待和打字速度

> **一句话：** 一次回复先是 32 ms 的 prefill，到第一个 token；之后每 4.9 ms 出一个 token，每个都是一次 decode。

### 图上是什么

- 时间轴 0 到 90 ms，按比例画。
- 蓝色长块「prefill · 32 ms 的计算」：第 7 步那次 2,000 token 的 prefill。
- 竖虚线「第一个 token」：prefill 结束处。
- 后面一串橙色小块：每块一次 decode 步，一块一个 token，共 11 块。
- 说明行：「之后每 4.9 ms 出一个 token：权重和 prompt 的 cache 再读一遍」。

### 公式

decode 小块用第 6 步的公式，$c = 2{,}000$：

$$
t_{\text{mem}} = \frac{M_W + c \times 128\ \text{KB}}{BW}
$$

### 代入图上的数

| 量 | 计算 | 结果 | 图上 |
|---|---|---|---|
| prefill | 第 7 步 | 32.4 ms | 32 ms |
| $M_{KV}$，$c = 2{,}000$ | 2,000 × 128 KB | 0.256 GB | |
| 一个 decode 步 | (16 + 0.256) ÷ 3.35 | 4.85 ms | 4.9 ms |
| 每秒 token 数 | 1,000 ÷ 4.85 | 约 206 个 | |
| prefill 之后剩下的时间 | 90 − 32.4 | 57.6 ms | |
| 放得下几块 | 57.6 ÷ 4.85 = 11.9，取整 | 11 块 | 11 块 |

### 两个常用指标

- **首 token 时间（TTFT，time to first token）**：发出请求到第一个 token 的时间。这里由 prefill 的计算决定。
- **token 间隔**：之后相邻两个 token 的时间，也就是打字速度。这里由 decode 的读取决定。

图上 decode 小块画成一样长。实际每块比前一块稍长：每个新 token 让 $c$ 加 1，cache 多 128 KB，每步多约 0.00004 ms。

第 10 步回到 decode 的那 0.3%。

## 第 10 步 · decode 时 GPU 几乎一直闲着

> **一句话：** 一个 decode 步计算单元只忙 0.3%，产出一个用户的一个 token；如果一步里放多个用户的 token 呢？

### 图上是什么

- 和第 5 步同一张图：1 个橙色 token，读取 16 GB，内存条 4.8 ms，计算条 0.016 ms。
- 计算框换成红色粗边框，忙碌标签变成红色粗体「忙碌占这一步的 0.3%」。

### 代入图上的数

| 量 | 计算 | 结果 |
|---|---|---|
| 忙碌 | 0.0162 ÷ 4.78 | 0.3% |
| 闲置 | 100% − 0.3% | 99.7% |
| 这一步产出 | | 1 个序列的 1 个 token |

### 闲置能怎么用

第 8 步的图：$n$ 在 295 以下，$t_{\text{step}}$ 都是 4.8 ms。第 3 步里 5 个 prompt token 共用一次读取。如果一步里的 $n$ 个 token 来自 $n$ 个不同用户、各自 decode 自己的下一个 token，它们也能共用这一次 16 GB 的读取。

每个用户有自己的 cache，各自的 $M_{KV}$ 还得分别读。第 5 章的图只算权重读取，cache 随用户数增长的读取量在第 14 章再算。

### 接下来

第 5 章把多个用户的 decode 放进同一步，这叫 batching。
