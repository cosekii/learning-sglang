## 第 1 步 · 量首个 token 前的等待

**一句话。** TTFT 告诉你：用户要等多久，才能看到回答的第一个 token。

**图上是什么。** 动画先画出请求在 0 ms 发出，再画出首个 token 在 250 ms 出现，最后列出减法。蓝色只标这两个时刻之间的等待。这里的 `stream: true` 表示打开流式返回：服务器分多次发 delta，而不是一次发完整回答。这个构造例中，每个 SSE delta 恰好携带一个输出 token；250 ms 是客户端读到第一个 delta 的时刻。这个例子的等待包含排队与 prefill，但图中没有把两者分别测成多少毫秒。

**公式与符号。**

$$\mathrm{TTFT}=t_{\mathrm{first\ token}}-t_{\mathrm{request\ sent}}$$

- $\mathrm{TTFT}$：time to first token，也就是首个 token 前的等待。
- $t_{\mathrm{request\ sent}}$：请求发出的时刻，图中是 0 ms。
- $t_{\mathrm{first\ token}}$：首个输出 token 出现的时刻，图中是 250 ms。
- $\mathrm{ms}$：毫秒；$1{,}000\ \mathrm{ms}=1$ 秒。

**代入图上的数。**

$$\mathrm{TTFT}=250-0=250\ \mathrm{ms}=0.250\ \mathrm{s}=\frac14\ \mathrm{s}$$

250 ms 是 zero-to-sglang 第 1 部分第 5 章 §3.1 的构造教学值，不是本机实测。《Inference Engineering》§1.4 使用同样的测量边界：从请求发出到首个输出 token 出现。本步没有分别测量排队、prefill 和后续回答各花多久。

**接下来。** 首个 token 已经出现；下一把尺子要量相邻输出 token 之间的间隔。

## 第 2 步 · 量相邻 token 的间隔

**一句话。** ITL 是相邻两个输出 token 出现时刻的差，每一段都可以单独测量。

**图上是什么。** 动画依次画出第 2、3、4 个 token，以及每个 token 前的间隔。从请求发出开始计时，四个 token 分别在 250、275、295、325 ms 出现。每个时刻都记录客户端读到对应 SSE delta 的时间。三段蓝色箭头分别标出 25、20、30 ms；蓝色只表示 ITL，不包括首个 token 前的 TTFT。

**公式与符号。**

$$\mathrm{ITL}_i=t_i-t_{i-1}\quad(i=2,3,4)$$

- $\mathrm{ITL}_i$：inter-token latency，第 $i$ 个输出 token 与前一个输出 token 的间隔。
- $t_i$：第 $i$ 个输出 token 出现的时刻；$t_1$ 是第 1 步首个 token 的 250 ms。
- $i$：输出 token 的编号，从 1 开始；本步量第 2、3、4 个 token 前的三段间隔。
- $\mathrm{ms}$：毫秒，沿用上一步的单位。

**代入图上的数。**

$$\mathrm{ITL}_2=275-250=25\ \mathrm{ms}$$

$$\mathrm{ITL}_3=295-275=20\ \mathrm{ms}$$

$$\mathrm{ITL}_4=325-295=30\ \mathrm{ms}$$

zero-to-sglang 第 1 部分第 5 章 §3.1 与《Inference Engineering》§1.4 都把 ITL 定义为相邻输出 token 的时间间隔。第 2 至第 4 个时刻是在同一构造请求上补写的教学值，不是本机实测；三段间隔不必一样长。

**接下来。** 三段间隔已经分别量出；下一步把它们合成一个平均值。

## 第 3 步 · 求首个 token 后的平均间隔

**一句话。** TPOT 把首个 token 后的各段 ITL 合成一个平均值。

**图上是什么。** 同一个时钟再次依次显示 250、275、295、325 ms 四个时刻，以及 25、20、30 ms 三段蓝色 ITL。三段都出现后，图上才列出平均值的算式；首末时刻也算出同一个结果。TPOT 不含第 1 步的 TTFT，平均也不表示三段间隔变得一样长。

**公式与符号。**

$$\mathrm{TPOT}=\frac{\sum_{i=2}^{N}\mathrm{ITL}_i}{N-1}=\frac{t_N-t_1}{N-1}\quad(N\ge2)$$

- $\mathrm{TPOT}$：time per output token；本例是首个 token 之后，每段相邻输出间隔的平均值。
- $N$：输出 token 的总数，本例为 4；$N-1$ 才是首个 token 后的间隔数。
- $\mathrm{ITL}_i$：第 2 步量出的第 $i$ 个 token 与前一个 token 的间隔。
- $t_1$、$t_N$：第 1 个和最后一个输出 token 的时刻，本例分别为 250、325 ms。
- $\sum_{i=2}^{N}$：从第 2 个 token 到第 $N$ 个 token，把各段 ITL 加起来。

**代入图上的数。**

$$\mathrm{TPOT}=\frac{25+20+30}{4-1}=\frac{75}{3}=25\ \mathrm{ms}$$

$$\mathrm{TPOT}=\frac{325-250}{4-1}=\frac{75}{3}=25\ \mathrm{ms}$$

zero-to-sglang 第 1 部分第 5 章 §3.1 用同样的边界：输出 200 个 token 时，扣除首个 token 后按 199 段计算，课程常把单位写成 ms/token。本例的 25 ms 恰好等于第一段 ITL，但另外两段仍是 20、30 ms；请求发出到首个 token 的 250 ms TTFT 没有进入分子。

**接下来。** 首个 token 前的等待和后续平均间隔都已量出；下一步可以量整个回答从头到尾的总时间。

## 第 4 步 · 量请求的完整时间

**一句话。** E2E 总延迟从请求发出算到请求完成，把首个 token 前和后的时间都算进去。

**图上是什么。** 上方蓝线沿同一个时钟走过 250、275、295、325 ms。请求在 0 ms 发出，第 1 个 token 在 250 ms 出现，客户端在 325 ms 读到携带第 4 个 token 的最后一个 SSE delta。下方两段分别标出 TTFT 的 250 ms 和首个 token 后的 75 ms；卡片间距只是排版示意，不是另一把时间尺。完成后才列出完整 E2E 算式。75 ms 仍是第 2 步三段 ITL 的总和，不是只取一段，也不是只加一次平均 TPOT。

**公式与符号。**

$$\mathrm{E2E}=t_{\mathrm{complete}}-t_{\mathrm{request\ sent}}=\mathrm{TTFT}+\sum_{i=2}^{N}\mathrm{ITL}_i$$

- $\mathrm{E2E}$：end-to-end latency，从请求发出到全部完成的总延迟。
- $t_{\mathrm{request\ sent}}$：请求发出的时刻，图中是 0 ms。
- $t_{\mathrm{complete}}$：请求完成的时刻；本例把携带最后一个 token 的 SSE delta 在 325 ms 到达视为完成。
- $\mathrm{TTFT}$：第 1 步量出的首 token 前等待，本例为 250 ms。
- $\sum_{i=2}^{N}\mathrm{ITL}_i$：从第 2 个到第 $N$ 个 token，把所有相邻间隔相加；本例 $N=4$。

**代入图上的数。**

$$\mathrm{E2E}=325-0=325\ \mathrm{ms}$$

$$\mathrm{E2E}=250+(25+20+30)=250+75=325\ \mathrm{ms}$$

zero-to-sglang 第 1 部分第 5 章 §3.1 将 E2E 定义为请求从发出到全部完成的总时长，并用 $\mathrm{E2E}=\mathrm{TTFT}+\text{剩余生成时间}$ 计算。本例沿用同一边界；0、250、325 ms 都是构造教学值，不是本机实测，也没有另列最后 token 之后的处理时间。

**接下来。** 一个请求的完整时间已经量出；下一步把多个请求放在一起，找出其中较慢的请求。

## 第 5 步 · 排序两批请求并比较 P50

**一句话。** 把两批各 100 个请求放在同一延迟刻度上排序，再比较两批排在中间的 E2E 总延迟。

**图上是什么。** 每根蓝色柱子是一个请求的 E2E 总延迟。两块面板都从乱序开始，先给 A 排序，再给 B 排序。A 有 51 个 200 ms、48 个 300 ms 和 1 个 2000 ms；B 有 50 个 250 ms、49 个 400 ms 和 1 个 2000 ms。随后第 50 个位置出现 P50 标签：A 是 200 ms，B 是 250 ms。两块面板共用 0–2000 ms 刻度，最后一行算出 B − A = 50 ms。

**公式与符号。** 对任意一批 $b\in\{A,B\}$，本步把排在 50% 位置的总延迟叫 P50：

$$L^b_{(1)}\le L^b_{(2)}\le\cdots\le L^b_{(N)},\qquad r=\lceil0.50N\rceil,\qquad \mathrm{P50}^b=L^b_{(r)}$$

- $b$：批次标签，A 或 B。
- $L^b_{(i)}$：批次 $b$ 排序后第 $i$ 个请求的 E2E 总延迟；量法来自第 4 步。
- $N$：每批请求总数，都是 100。
- $r$：排到 50% 时的位置；$\lceil\ \rceil$ 表示向上取整。
- $\mathrm{P50}^b$：批次 $b$ 排在 $r$ 位置的总延迟，不是这批请求的平均值。

**代入图上的数。**

$$\mathrm{P50}^A=L^A_{(\lceil0.50\times100\rceil)}=L^A_{(50)}=200\ \mathrm{ms}$$

$$\mathrm{P50}^B=L^B_{(50)}=250\ \mathrm{ms},\qquad \mathrm{P50}^B-\mathrm{P50}^A=250-200=50\ \mathrm{ms}$$

$$L^A_{(100)}=2000=10\times200\ \mathrm{ms},\qquad L^B_{(100)}=2000=8\times250\ \mathrm{ms}$$

A 沿用 zero-to-sglang 第 1 部分第 5 章 §5.2 的构造情境：99 个较快请求和 1 个 2 s 请求。B 是为了同刻度比较另写的构造分布。两批都不是本机实测。课程 §5.1 和《Inference Engineering》§1.4.1 都把 P50 放在排序后的中间位置。作为图外对照，把第 50、51 个等待取平均时，A 仍得 200 ms，B 则得 $(250+400)\div2=325$ ms；图上两批都使用上面写明的取位方法。其他数据集或工具可能用插值求 P50，本步不展开。

**接下来。** 两批的中间位置已经找到；下一步在同一两批排序结果中比较第 99 个请求。

## 第 6 步 · 比较同一两批请求的 P99

**一句话。** P99 取第 99 个请求的 E2E 总延迟：A 是 300 ms，B 是 400 ms；两批最慢请求都是 2000 ms。

**图上是什么。** A、B 保留第 5 步排好的柱子和 0–2000 ms 刻度。动画先标出 A 的第 99 个请求和 300 ms P99，再标出它与最慢请求相差 1700 ms。随后对 B 做同样的测量：P99 是 400 ms，与最慢请求相差 1600 ms。每批都有 99 个请求不超过各自的 P99。

**公式与符号。** 沿用第 5 步的取位方法，对批次 $b\in\{A,B\}$：

$$L^b_{(1)}\le L^b_{(2)}\le\cdots\le L^b_{(N)},\qquad r=\lceil0.99N\rceil,\qquad \mathrm{P99}^b=L^b_{(r)}$$

- $b$：批次标签，A 或 B。
- $L^b_{(i)}$：批次 $b$ 排序后第 $i$ 个请求的 E2E 总延迟。
- $N$：每批请求总数，都是 100。
- $r$：排到 99% 时的位置；$\lceil\ \rceil$ 表示向上取整。
- $\mathrm{P99}^b$：批次 $b$ 排在 $r$ 位置的总延迟，不是平均值，也不必然等于最慢请求。

**代入图上的数。**

$$\mathrm{P99}^A=L^A_{(\lceil0.99\times100\rceil)}=L^A_{(99)}=300\ \mathrm{ms}$$

$$\mathrm{P99}^B=L^B_{(99)}=400\ \mathrm{ms}$$

$$L^A_{(100)}-\mathrm{P99}^A=2000-300=1700\ \mathrm{ms}$$

$$L^B_{(100)}-\mathrm{P99}^B=2000-400=1600\ \mathrm{ms}$$

zero-to-sglang 第 1 部分第 5 章 §5.1 要求同时观察 P50 和 P99，用 P99 看较慢的请求；§5.2 用 99 个较快请求和 1 个 2 s 请求说明平均值会遮住那 1 个慢请求。两批分布都是构造教学例，不是本机实测。课程没有规定这个取位公式；两块面板都沿第 5 步使用向上取整，其他工具可能采用插值，本步不展开。

**接下来。** 两批的中间和靠后等待都已量出；下一步数清每批在整个测试中完成多少个请求。

## 第 7 步 · 比较两批请求的吞吐量

**一句话。** 吞吐量用完成请求数除以整批测试时长，所以 A 是 5 requests/s，B 是 4 requests/s。

**图上是什么。** 每块面板有 100 个请求格，两条整批时钟共用 0–25 s 刻度，0 s 是客户端开始测试的时刻。A 的时钟走过 5、10、15、20 s，方格每次增加 25 个蓝色完成格。随后 B 走过 5、10、15、20、25 s，每次增加 20 个。同一刻度把 A 的终点留在 20 s，把 B 的终点留在 25 s。均匀填格只是画图简化，不表示固定完成间隔。客户端读到某个请求的最后一个 SSE delta 时，该请求完成。请求重叠执行，所以第 5、6 步的单请求 E2E 不能相加成整批窗口。20 s 时 A 完成 100 个，吞吐量是 $100\div20=5$ requests/s；25 s 时 B 完成 100 个，结果是 $100\div25=4$ requests/s。两个测试窗口都不是一个请求的 E2E 总延迟。

**公式与符号。** 对批次 $b\in\{A,B\}$：

$$Q_b=\frac{N_{\mathrm{done},b}}{T_b}$$

- $b$：批次标签，A 或 B。
- $Q_b$：批次 $b$ 的请求吞吐量，表示单位时间完成多少请求。
- $N_{\mathrm{done},b}$：批次 $b$ 在整个测试中完成的请求数，两批都是 100。
- $T_b$：从客户端开始测试到最后一个请求完成的整批时长，A 为 20 s，B 为 25 s。
- $\mathrm{requests/s}$：每秒完成的请求数；`request` 就是第 5、6 步中的一个请求。

**代入图上的数。**

$$Q_A=\frac{100\ \mathrm{requests}}{20\ \mathrm{s}}=5\ \mathrm{requests/s}$$

$$Q_B=\frac{100\ \mathrm{requests}}{25\ \mathrm{s}}=4\ \mathrm{requests/s}$$

zero-to-sglang 第 1 部分第 5 章 §3.2 把 Throughput 定义为单位时间的产出，可用 `request/s` 计量，并要求与延迟同时观察。`src/ml-sys/numbers.ts` 中的 20 s 和 25 s 都是构造教学值，同一文件用两批各 100 个完成请求推导出结果。它们不是本机实测，也不代表 SGLang 的实际性能。每个吞吐量都是整段时间的平均值。本步只讲请求吞吐量，不展开 `token/s`、Goodput、SLA、请求集选择、预热或并发变化；第 14 章再讲控制变量的 profiling。

**接下来。** 本章已经量出两批请求的等待和完成量。下一章回到请求开始之前，看看显卡里已经装了什么，以及它们各占多少空间。
