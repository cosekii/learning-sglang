## 第 1 步 · 三样东西，不是一样

> **一句话：** 模型文件在磁盘上，模型进程在内存里跑，应用包是程序本身；模型装好应用后才下载，大小约是 0.1.0-beta.1 应用的九倍。

### 图上是什么

- 左边蓝色面板：**模型文件**，2.47 GB，模型库里九个文件，在磁盘的 Application Support 下，装好应用后才下载。
- 中间橙色面板：**语音服务器**，一个 ASR 进程，把模型读进内存，用完后还会留着，自动模式空闲十分钟请求停止。第 4 步再画旁边的 Silero VAD 服务器。
- 右边蓝色面板：**应用包**，公开文档里的 0.1.0-beta.1 构建是 280 MB，是用户打开的程序，与模型分开安装。
- 顶部算式：2,467,856,503 ÷ 280,000,000 ≈ 8.8，所以图上写约 9 倍。底部算式把最大文件和其余八个文件加起来。
- 图例：蓝色是磁盘上的文件，橙色是运行的程序。
- 下面三行：模型后来才下；自动模式会请求空闲服务器停止，文件留着；应用更新只换应用，不动模型文件夹。

### 公式

$$ \text{模型字节} = \sum_{f \in \text{文件}} \text{大小}(f), \qquad \text{倍数} = \frac{\text{模型字节}}{\text{应用字节}} $$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $f$ | 默认语音模型的一个文件 | 9 个文件 | `catalog.go:204-214` |
| $\text{大小}(f)$ | 这个文件的字节数 | 字节 | 目录里的 `File.Size` |
| 模型字节 | 九个文件加起来 | 2,467,856,503 B | 本步的求和 |
| 应用字节 | 公开文档里的 0.1.0-beta.1 应用包 | 280 MB | `docs/release.md` |
| 倍数 | 模型相对应用 | 8.8 | 本步 |

### 代入图上的数

| 量 | 算式 | 结果 |
|---|---|---|
| 其余八个文件 | $1{,}161 + 7{,}188 + 142 + 1{,}671{,}853 + 78{,}968 + 330 + 12{,}487 + 2{,}776{,}833$ | 4,548,962 B |
| 模型字节 | $2{,}463{,}307{,}541 + 4{,}548{,}962$ | 2,467,856,503 B = 2.47 GB |
| 倍数 | $2{,}467{,}856{,}503 \div 280{,}000{,}000$ | 8.8，图上写 9 倍 |

### 为什么是三样

应用里装的是跑模型的代码：Go 应用、Swift helper、omni 运行时的二进制（`docs/release.md`）。omni 运行时把下载的模型跑成独立的本地服务器，Voxt 再与服务器通信（`internal/omni/doc.go:1-5`、`31-35`）。应用不带模型权重。用户选好语音模型后，Voxt 把模型下载进模型库，默认是 `~/Library/Application Support/SGLang Omni/models`（`hub.go:106-119`）。ActNow 家族的其他应用可以共用这个库。280 MB 是文档记录的 0.1.0-beta.1 构建大小，不代表每个版本。

于是有三段不同的寿命。文件一直留着，直到有人删它。服务器进程在每次用完后，还会按设置的空闲时间留下来。应用内更新会替换应用包。把三者混在一起，就会产生错误期待，比如「更新应用就会下载新模型」或「删掉模型等于卸载应用」。

### 接下来

第 2 步看存下来的到底是什么：一个固定提交，和一张带哈希的文件清单。

## 第 2 步 · 固定的快照

> **一句话：** 目录给一个仓库、一个提交，以及每个文件的大小和指纹；LFS 用 SHA-256，其他文件用 git blob ID，快照文件夹使用完整提交。

### 图上是什么

- 左边蓝色卡片：模型的网上地址，仓库 `mlx-community/Qwen3-ASR-1.7B-8bit`，以及缩短显示的提交 `a8379a2`。固定快照就是一个确定的版本。
- 右边文件面板：九个文件，2.47 GB 来自第 1 步的求和。`model.safetensors` 是 2.46 GB，SHA-256 `bf304b…` 是根据字节算出的指纹；`vocab.json` 是 2.78 MB，git blob ID 是 git 的字节指纹；还有七个文件。
- 下面是磁盘路径 `models--mlx-community--Qwen3-ASR-1.7B-8bit` / `snapshots/a8379a2e2f9e313c9292cdf1af4055ab56d50d55`。文件夹用完整提交，不用短标签。
- 两行：仓库会变，所以提交固定了测试过的文件；指纹能发现文件变了或坏了。

### 公式

$$ \text{快照} = \operatorname{join}(\$HUB,\ \texttt{models--}\langle owner\rangle\texttt{--}\langle name\rangle,\ \texttt{snapshots},\ \langle commit\rangle) $$

$$ \text{LFS 文件：}\ \mathrm{SHA256}(\text{文件}) = \text{清单里的哈希}, \qquad \text{其他文件：git blob ID 一致} $$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $\$HUB$ | 模型库文件夹 | — | `hub.go:106-119` |
| 快照 | 保存一个提交的文件的文件夹 | — | `hub.go:89-104` |
| 文件 | 正在校验的一个清单文件 | 字节 | 目录 |
| $\langle owner\rangle$ | Hub 所有者 | `mlx-community` | 目录里的 `Repo` |
| $\langle name\rangle$ | Hub 仓库名 | `Qwen3-ASR-1.7B-8bit` | 目录里的 `Repo` |
| $\langle commit\rangle$ | 固定提交 | `a8379a2e…` | `catalog.go:203` |
| 哈希 | LFS 文件的 SHA-256 指纹 | 64 个十六进制字符 | 目录里的 `File.SHA256` |
| git blob ID | 非 LFS 文件的内容 ID | git 的 blob ID | `hub.go:28-44` |

### 代入图上的数

| 量 | 算式 | 结果 |
|---|---|---|
| 文件数 | 目录列出的 | 9 |
| 权重 | `model.safetensors` | 2,463,307,541 B = 2.46 GB |
| `vocab.json` | 2,776,833 B ÷ 1,000,000 | 2.78 MB |
| 总数 | 第 1 步的九文件求和 | 2,467,856,503 B = 2.47 GB |

### 为什么用提交，不用名字

Hugging Face 仓库在 tag 移动后可能加文件或改文件。目录里存的是提交 ID，所以应用只要它测试过的那批文件（`internal/models/catalog.go:105-114`）。`Accept` 再列几个运行时验证过的提交：磁盘上有其中一个，就用它，不再下固定的那个（`catalog.go:108-111`）。

完整性校验是另一半。大权重文件在 Hub 上放在 Git LFS（Large File Storage，大文件存储）里，blob 的名字就是 SHA-256（`catalog.go:84-94`）。`Entry` 只给 LFS 文件复制目录里的 SHA-256；下载按这个指纹核对，被截断或损坏会报错，不会加载。非 LFS 文件在下载条目里留空 SHA-256，改用 git blob ID 核对（`hub.go:28-44`、`internal/models/models_test.go:235-250`）。哈希是内容的指纹：字节相同，ID 就相同。

### 接下来

第 3 步跟一次下载：它带什么、什么时候能停、核对什么。

## 第 3 步 · 下载任务

> **一句话：** 一个任务下载模型和它需要的模型，取消时已经下到的字节留着，每个文件都核对，磁盘上还要留 2 GB。

### 图上是什么

- 上面板：下载进度条，已经下到的部分填上。红线是取消点；文字说下次从这里接着下。总共 2.47 GB。
- 三张卡片：**空位** 2 GB 必须空着；**校验** 每个文件，LFS 用 SHA-256，其他用 git blob ID，不对就报错；**一起装** 1.24 MB 的 Silero VAD，它是找出语音的小模型，也在同一个任务里。
- 公式：2,467,856,503 B + 1,238,323 B = 2,469,094,826 B；1,238,323 ÷ 2,469,094,826 × 100 ≈ 0.05%。
- `一起装` 表示模型需要 VAD；取消会保留已下载的文件。

### 公式

$$ \text{任务字节} = \sum_{m \in \text{任务}} \sum_{f \in m} \text{大小}(f), \qquad \text{VAD 占比} = \frac{\text{VAD 字节}}{\text{任务字节}} \times 100\% $$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| 任务 | 模型加上它需要的模型 | 2 个模型 | `manager.go:269-281` |
| $m$ | 任务里的一个模型 | — | 目录 |
| $f$ | $m$ 的一个文件 | — | 目录 |
| $\text{大小}(f)$ | 这个文件的字节数 | 字节 | 目录里的 `File.Size` |
| VAD 字节 | Silero VAD 的两个文件 | 1,238,323 B | `catalog.go:352-354` |
| 任务字节 | 任务总共要下的 | 2,469,094,826 B | 本步 |
| VAD 占比 | VAD 字节除以任务字节，再乘 100 | 0.050% | 本步的算式 |

### 代入图上的数

| 量 | 算式 | 结果 |
|---|---|---|
| 模型 | 九个文件 | 2,467,856,503 B |
| VAD | $463 + 1{,}237{,}860$ | 1,238,323 B |
| 任务 | $2{,}467{,}856{,}503 + 1{,}238{,}323$ | 2,469,094,826 B = 2.47 GB |
| VAD 占比 | $1{,}238{,}323 \div 2{,}469{,}094{,}826 \times 100$ | 0.050% |

### 取消后留下什么

`Manager.Download` 为模型和缺少的依赖组成一个任务，再把这个任务放到一个 goroutine 上。`run` 按顺序下载这些模型，不是每个模型一个 goroutine（`manager.go:254-291`、`319-339`）。`Cancel` 停掉任务，已经写进模型库的字节留着（`manager.go:293-303`）。下次下载看到半成品 blob 就接着下，不从头来（`internal/models/manager_test.go:458-482`）。停下的下载 `Done` 就是留下的字节（`manager.go:60-63`）。内容校验不对会报错，本章不声称会自动再下一遍。

开始之前，任务要在磁盘上留空位。`Options.ReserveBytes` 就是这个空位；零表示 hfhub 的 2 GB（`manager.go:33-35`）。磁盘快满时，下载在填满最后一点之前就失败。

任务还带上条目需要的模型。默认语音模型在 `Needs` 里列了 Silero VAD，所以全新安装会两个都下（`catalog.go:201`、`manager.go:269-281`）。装过第一个语音模型后，VAD 已经在磁盘上，下一个任务就跳过它（`manager.go:270-272`）。Silero 是找出语音的小模型。第 3 章第 6 步的能量检测器按响度找语音；Silero 接过这个检测工作，能量检测器留作回退（`internal/omni/doc.go:77-83`）。第 4 步画出它独立的服务器。

### 接下来

第 4 步从文件转到读文件的进程。

## 第 4 步 · 语音服务器

> **一句话：** 文件留在磁盘上；用模型会启动独立的服务器进程，自动模式空闲十分钟后请求停止，设置可以改变这个时间。

### 图上是什么

- 左边蓝色面板：**在磁盘上**，快照文件夹 `Qwen3-ASR-1.7B-8bit`，2.47 GB，服务器退出后还留着。
- 右边橙色面板：**在内存里**，`qwen3_asr_server` 从文件夹读入一个 ASR 模型，Silero VAD 有自己的小服务器。自动模式用十分钟空闲时间；下次用会重启。
- 下面板：**删除模型文件**先请求卸载，再请求删文件，不等待进程退出。忙碌服务器等用完再停。
- 空闲计时只发出停止请求（`server.go:241-251`）；进程退出时卸载才算完成（`process.go:188-205`）。
- 脚注：设置可选 5、15、30 或 60 分钟，也可以一直留到退出应用。

### 公式

$$ t_{\text{停止请求}} = t_{\text{最后使用}} + T_{\text{空闲}} \quad (T_{\text{空闲}} \ge 0), \qquad T_{\text{空闲}} < 0 \Rightarrow \text{不因空闲停止} $$

$$ \text{启动 180 秒仍不能接受识别} \Rightarrow \text{启动失败并停止进程} $$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $t_{\text{最后使用}}$ | 最后一次使用服务器结束 | — | `server.go:60-64`、`215-229` |
| $T_{\text{空闲}}$ | 设置的未使用时长；负数关闭空闲卸载 | 自动模式 10 分钟 | `settings/models.go:105-135`、`server.go:231-251` |
| $t_{\text{停止请求}}$ | 未使用的服务器什么时候被请求停止 | $t_{\text{最后使用}} + T_{\text{空闲}}$ | `DefaultIdleTimeout`，`runtime.go:31` |
| 180 秒 | 就绪超时，不是承诺的加载时间 | 秒 | `DefaultStartTimeout`，`runtime.go:30`、`44-46` |

### 代入图上的数

| 设置或事件 | 代码怎么做 |
|---|---|
| 自动模式 | $T_{\text{空闲}} = 10$ 分钟 |
| 设置 | 5、15、30 或 60 分钟；留到退出应用会关闭空闲计时器 |
| 停止后再次使用 | 重新启动服务器 |
| 启动 180 秒 = 3 分钟后仍不能接受识别 | 启动失败并停止进程 |

### 为什么要有进程

运行时二进制在应用包里，但读进内存的模型不是应用。`Runtime` 在获取模型时启动服务器并看着它（`runtime.go:122-143`、`191-228`）。服务器从快照文件夹读模型，所以进程跑着的时候文件必须留着。Silero VAD 有自己的 `silero_vad_server`，第一次使用时在 ASR 服务器旁边启动（`internal/omni/models.go:60-63`、`internal/omni/vad.go:23-44`）。

一次只跑一个语音模型。切换到一个语音模型，其他语音模型的服务器就停止接收新任务，等当前使用结束后退出（`runtime.go:191-228`）。自动模式保留运行时的十分钟默认值。设置把 `KeepLoaded` 交给 `SetIdleTimeout`：5、15、30 或 60 分钟，或者用负数表示留到退出应用（`models_controller.go:280-306`、`settings/models.go:105-135`）。第一次加载可能编译 Metal kernel；180 秒超时会停止一直没有就绪的服务器（`runtime.go:29-30`、`44-46`）。

删模型不只是磁盘操作。`Library.Delete` 调用 `Unload` 后，立刻请求 `models.Manager.Delete`，不等待服务器的 `stopped` 通道（`internal/local/library.go:70-82`、`runtime.go:249-266`）。`Unload` 让服务器停止接收新任务。空闲进程异步停止，忙碌进程等使用结束后停止（`server.go:215-229`、`253-287`）。`unloadOmni` 也会让被删 draft 所属的语音模型停止接收新任务（`models_omni.go:293-316`）。删除请求经过外部 actnowkit；本章不声称忙碌模型会删除成功，也不声称文件一定保留（`internal/models/claims.go:40-54`）。

## 第 5 步 · 应用更新走另一条路

> **一句话：** 有 Voxt 签名更新源时，更新器替换应用，重启后完成；没有更新源的发布版本提供外部安装包，两条路都不动模型文件夹。

### 图上是什么

- 左面板：有更新清单时的应用内更新。构造示例是正在运行的 `Voxt 2.0` 和磁盘上的 `Voxt 2.1`，更新器替换整个应用包。
- 右面板：没有更新源的发布版提供匹配的 DMG；没有匹配的 DMG 就提供发布页。用户下载安装，应用不直接替换自己。开发版没有更新路线。
- 中间横条：**模型文件夹**，`SGLang Omni/models`，2.47 GB，两条更新路线都不碰它。
- 下面 **重启之前** 的流程：旧版本照常运行 → 磁盘上的 helper 已经是新的 → 应用的 helper 管理器和它版本对不上，不启动它。

### 公式

$$ \text{应用内更新完成} \iff \text{应用包已替换} \land \text{应用已重启} $$

| 符号 | 是什么 | 从哪来 |
|---|---|---|
| 应用内更新完成 | 新版本已经可以正常接管 | 本步的完成条件 |
| 应用包已替换 | 磁盘上的 `Voxt 2.1` 已代替 `Voxt 2.0` | 图上的构造示例 |
| 应用已重启 | 运行中的旧进程已经换成新进程 | `updates.go:245-253` |

### 代入图上的数

| 应用包已替换 | 应用已重启 | 结果 |
|---|---|---|
| 是，磁盘上是 `Voxt 2.1` | 否，仍运行 `Voxt 2.0` | 还没完成，卡片请用户重启 |
| 是 | 是 | 应用内更新完成 |

### 更新的几部分

| 部分 | 发生什么 | 从哪来 |
|---|---|---|
| 检查 | 默认每 24 小时一次；用户可以关掉自动检查 | `Voxt/updates.go:68-74`、`179-209`；`updates_github.go:361-387` |
| 安装 | 默认由用户安装；可选的自动安装可以不询问就装 | `updates.go:4-6`、`179-209`；`docs/release.md:406-410` |
| 有更新源时替换 | 更新器在旧版本运行时替换 `Voxt.app`，有增量就用增量 | `updates.go:12-16` |
| 无更新源时回退 | 发布构建不能直接更新自己；有匹配的 dmg 就下载，没有匹配时才打开发布页 | `updates_github.go:3-18`、`361-387` |
| 对不上 | 磁盘上的 helper 是新版本的，管理器不启动它 | `updates.go:12-16` |
| 重启 | 卡片提供 Restart Voxt，重启后完成应用内更新 | `updates.go:245-253` |
| 监视 | 运行中的应用每分钟看一次是否已装好 | `updates.go:114-116`、`213-228` |
| 更新源 | 签名 feed、GitHub 回退，或没有更新器 | `internal/updates/updates.go:13-22`、`main.go:127-136` |

### 为什么要重启

有签名更新源时，更新器换的是磁盘上的文件，正在运行的进程还用着启动时的代码。helper 是磁盘上的另一个程序，换过之后它属于新版本。supervisor 是应用里负责启动 helper 的管理器。它把 helper 和运行中的应用比对，版本对不上就不启动（`updates.go:12-16`）。所以在重启之前，转写可能停掉，或者弹出卡片。

只有发布构建支持更新，开发构建不会替换自己。没有更新源的发布构建走 GitHub 回退，给用户提供外部安装包（`updates_github.go:3-18`）。beta 通道是设置里的开关，当前版本自己是 beta 时默认打开（`updates.go:18-24`、`187-203`）。发布构建的 beta 和 stable 都能使用这套通道逻辑。

模型文件夹在这件事里没有角色。应用更新替换或下载 `Voxt.app`，不下载、不删除、不移动模型文件。反过来也一样：删模型不改应用。`2.0 → 2.1` 是构造的示例，不是真实测过的一次发布更新。

### 接下来

第 6 步把三种机制放进一张表。

## 第 6 步 · 三件事，三种收尾

> **一句话：** 下载在内容校验通过时结束，卸载在进程退出时结束，应用内更新在应用重启后结束；三件事谁都不替谁干。

### 图上是什么

| 东西 | 动作 | 算完成的条件 |
|---|---|---|
| 模型文件 | 下载 | 内容校验全部通过，文件进入模型库 |
| 语音服务器 | 卸载 | 进程退出，内存释放 |
| 应用包 | 应用内更新 | 应用包被替换，应用重启 |

- 三条边界：更新应用不下载模型；停服务器不删文件；删模型不更新应用。
- 章末画出一场会议，以及麦克风和其他应用的声音两个候选来源，问 Voxt 会录下哪些声音。

### 公式

$$ \text{下载完成} \iff \text{校验通过} \land \text{文件在模型库} $$
$$ \text{卸载完成} \iff \text{服务器进程已退出} $$
$$ \text{应用内更新完成} \iff \text{应用包已替换} \land \text{应用已重启} $$

| 符号 | 是什么 | 从哪来 |
|---|---|---|
| 下载完成 | 模型文件可以使用的完成条件 | 第 3 步 |
| 校验通过 | 每个文件都与自己的内容指纹一致 | 第 2、3 步 |
| 文件在模型库 | 文件已在磁盘上的模型库里 | 第 1、2 步 |
| 卸载完成 | 服务器不再占用内存的完成条件 | 第 4 步 |
| 服务器进程已退出 | 运行模型的程序已经停止 | 第 4 步 |
| 应用内更新完成 | 新版本已经可以正常接管 | 第 5 步 |
| 应用包已替换 | 磁盘上的新应用包已代替旧包 | 第 5 步 |
| 应用已重启 | 新进程已经代替旧进程 | 第 5 步 |

### 代入图上的数

| 动作 | 本步代入的完成条件 |
|---|---|
| 下载 | 内容校验通过，并且文件在模型库 |
| 卸载 | 服务器进程退出，内存随之释放 |
| 应用内更新 | `Voxt 2.1` 已替换 `Voxt 2.0`，并且应用已重启 |

### 为什么边界重要

每种机制有自己的触发和成功条件。下载可能因网络、磁盘满或内容校验不对而失败（`internal/models/manager.go:319-384`）。还在使用不是卸载失败：服务器停止接收新任务后，会等这次使用结束，没有固定时限（`runtime.go:249-266`、`server.go:215-229`）。有更新源的更新可能换完后不接受 helper，重启解决（`updates.go:12-16`）。没有更新源的发布构建改走外部安装包。

分开之后，第 1 步的两个期待就有了解释。更新应用带不来新模型，因为模型不在应用包里。删模型也腾不出应用自己的磁盘空间，因为应用不在模型库里。这些机制分别给出不同的提示和卡片。

本章讲默认本地 ASR 快照、它的 Silero 依赖和两条发布更新路线。没有测下载速度，没有真的更新应用，也不把 280 MB 当成 0.1.0-beta.1 以外版本的大小。
