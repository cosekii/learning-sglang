## 第 1 步 · 同一个 system prompt，存了两份

> **一句话：** req A 和 req B 的前 512 个 token 相同，照第 7 章的分页各存一份，同样的 64 MB k 和 v 写了两遍。

### 图上是什么

- 行标题：两个 prompt · 这里 page = 128 个 token。
- 两根 prompt 条：浅蓝色的「system prompt · 512 个 token」，后面接各自的问题，A 是蓝色的 qA · 140，B 是紫色的 qB · 90。
- 条右边：A「= 4 + 2 个 page」，B「= 4 + 1 个 page」。
- 下方 20 × 4 的 page 网格：蓝色格属于 A，紫色格属于 B，标 `S` 的是 system prompt 的 page；白色虚线格是空闲。
- 一条红色虚线连着 A 的最后一个 S page 和 B 的第一个 S page，旁边红字：S = 同样 512 个 token 的 k 和 v，存了两遍。
- 网格下两行 page table：A: 3, 9, 16, 22 | 31, 37；B: 46, 52, 59, 65 | 73。竖线左边是 system prompt 的 page，右边是问题的 page。

### 为什么两份数字完全一样

第 2 章第 3 步：位置 $i$ 的 key 和 value 是 $k_i = W_K x_i$、$v_i = W_V x_i$。$W_K, W_V$ 对所有 request 都是同一组权重。在第 1 层，$x_i$ 由 token id 查表得到（第 2 章第 2 步）；算出的 $k_i$ 还要按位置 $i$ 旋转一次（Llama 的位置编码，叫 RoPE）。所以同一位置上同一个 token id，给出同样的 $k_i, v_i$。第 2 层以后的情况，第 3 步再讲。

### 公式

$$
\text{pages}(n) = \left\lceil \frac{n}{p} \right\rceil,\qquad
M(n) = n \times m_{kv}
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $n$ | 一段 token 的个数 | | 本步 |
| $p$ | page 大小，一页装几个 token | 图上取 128 | 第 7 章第 6 步 |
| $\lceil\ \rceil$ | 向上取整：不满一页也要占一整页 | | |
| $\text{pages}(n)$ | 存 $n$ 个 token 要几个 page | | 本步 |
| $m_{kv}$ | 一个 token 在全部层的 k 和 v | 128 KB | 第 3 章第 9 步；`KB_PER_TOKEN` |
| $M(n)$ | $n$ 个 token 的 k 和 v 的字节数 | | 本步 |

图上的 $p = 128$ 只是为了网格画得下；SGLang 默认 $p = 1$（第 7 章第 6 步）。system prompt 和问题分开取整，所以 A 是 $4 + 2$ 而不是 $\lceil 652 / 128 \rceil = 6$，图上就是这样画的。

### 代入图上的数

| 量 | 计算 | 结果 |
|---|---|---|
| A 的 page | $\lceil 512/128 \rceil + \lceil 140/128 \rceil = 4 + 2$ | 6 |
| B 的 page | $\lceil 512/128 \rceil + \lceil 90/128 \rceil = 4 + 1$ | 5 |
| 池里共用掉 | 6 + 5 | 11 |
| 重复的 S page | 2 × 4 | 8 个里有 4 个是多余的 |
| system prompt 的 k 和 v | $512 \times 128$ KB = 65,536 KB | 64 MB，存了两份 |

除了多占的 64 MB，B 的 prefill 还把这 512 个 token 重算了一遍。

### 接下来

第 2 步让 B 的 page table 直接写 A 的页号。

## 第 2 步 · B 的 page table 指向 A 的 page

> **一句话：** B 的前 4 项改成 A 的 S page，池里少用 4 个 page，B 只 prefill 尾部 90 个 token；共享的 page 有了引用计数 2。

### 图上是什么

- 同样两根 prompt 条和网格。
- 网格里 A 的 4 个 S page 变成蓝紫相间的斜纹：两个 request 共用。B 原来的 4 个紫色 S page 消失。
- page table：A 不变；B 变成 **3, 9, 16, 22**（蓝色，就是 A 的页号）| 73，后面灰字：共享 page：2 个主人 · B 只 prefill 了 90 个 token，不是 602 个。

### 为什么可以这样做

page table 只是一串页号，attention kernel 按表去池里读 k 和 v（第 7 章第 7 步）。没有规则要求一个页号只出现在一张表里。两张表写同一个页号，两个 request 就读同一份数据，不用拷贝。

### 代入图上的数

| 量 | 计算 | 结果 |
|---|---|---|
| 池里用掉的 page | 11 − 4 | 7 |
| 省下的内存 | 第 1 步的第二份 | 64 MB |
| B 的 prompt | 512 + 90 | 602 个 token |
| B 实际 prefill | 602 − 512 | 90 个 token |

这 90 个 token 做 attention 时，前 512 个位置的 k 和 v 直接从第 3、9、16、22 页读，和读普通的 KV cache 一样（第 3 章第 6 步）。

### 引用计数

- **引用计数**：一个 page 现在被几个运行中的 request 使用。这 4 个 S page 是 2，A 和 B 各算一个。
- 第 7 章第 5 步里 page 只有一个主人，主人结束就还回池里。现在一个 request 结束只让计数减 1。
- 计数降到 0（A 和 B 都结束）时，caption 说的「释放」在 SGLang 里是**变成可回收**：page 默认留在 prefix cache 里，池子不够时才真正收回。第 7 步讲这一点。

### 接下来

第 3 步回答：B 怎么知道哪些 page 能和 A 共享。

## 第 3 步 · 只有前缀能复用

> **一句话：** 从第 1 个 token 起逐个比较 token id，第一个不同的位置 $d$ 之前的 $m = d - 1$ 个位置能复用，$d$ 及之后哪怕 token 相同也不能。

### 图上是什么

- A 的 prompt 条下方一排绿色 ✓，沿着 system prompt 一路过去：这些位置 token id 相同。（✓ 只画了 13 个，代表全部 512 个位置。）
- system prompt 末尾一个红色 ✕，旁边红字：第一个不同处：后面全是新的。这是 qA 的第一个 token 对 qB 的第一个 token。
- 网格和 page table 同第 2 步。
- 最下面一行：这就是为什么叫前缀缓存而不是子串缓存：匹配必须从第 1 个 token 开始。

### 公式

$$
m = d - 1
$$

| 符号 | 是什么 | 从哪来 |
|---|---|---|
| $d$ | 两个 prompt 第一个 token id 不同的位置 | 本步，图上的 ✕ |
| $m$ | 匹配长度：能复用 k 和 v 的位置数，即位置 $1 \dots m$ | 本步 |

图上 $d = 513$，所以 $m = 512$，正是 system prompt 的长度。

### 为什么 $d$ 之后不能复用

- **第 1 层**：$k_i, v_i$ 只由 token $i$ 和位置 $i$ 决定（第 1 步）。
- **第 2 层起**：第 2 层的 $x_i$ 是第 1 层在位置 $i$ 的输出。第 2 章第 6 步，attention 的输出是 $\text{out}_i = \sum_{j \le i} w_j v_j$，对所有 $j \le i$ 求和，$w_j$ 是第 2 章第 5 步的 softmax 权重。所以第 2 层的 $k_i, v_i$ 依赖 token $1 \dots i$。
- 改掉第 $d$ 个 token，位置 $d, d+1, \dots$ 在第 2–32 层的 k 和 v 都变了，哪怕这个位置自己的 token id 相同。
- 位置 $1 \dots d-1$ 的求和里没有 $d$（第 2 章第 7 步的因果遮罩：位置只看自己和之前的），所以不变。

结论：两个 prompt 中间恰好有一段相同的 token，也不能复用那一段。缓存只能按前缀查找。

### 接下来

第 4 步：很多 request 时，前缀之间互相嵌套，存成一棵树。

## 第 4 步 · 前缀存成 radix tree

> **一句话：** system prompt 是根，few-shot 集是第二层，各 request 的问题是叶子；每个节点只存一次，4 个 request 的 3,558 个 token 只占 1,472 个 token 的缓存。

### 图上是什么

- 行标题：缓存的前缀构成 radix tree · 每个节点持有其 token 的 page。
- 根：蓝框「system prompt · 512 个 token」。
- 第二层两个蓝框：few-shot 集 A · 300，few-shot 集 B · 250。
- 叶子四个橙框：q1 · 90、q2 · 140（在集 A 下），q3 · 60、q5 · 120（在集 B 下）。
- 底部一行：4 段对话，system prompt 只存一份：512 个 token 的缓存，而不是 2048 个 · 叶子是运行中的 request。

### 树怎么读

- 一个节点存一段连续的 token，并持有这段 token 的 k 和 v 所在的 page。
- 一个 request 的 prompt = 从根走到它那片叶子，路上所有节点依次拼起来。例如 q1 的 prompt 是 system prompt + 集 A + q1。
- 叫 **radix tree**（基数树）是因为一个节点存一整段，而不是一个 token 一个节点；只在两个 prompt 分叉的地方（第 3 步的 $d$）才拆成两个子节点。
- SGLang 里这棵树是 `RadixCache`，用它复用 KV cache 的做法叫 RadixAttention。

### 公式

$$
\text{不共享} = \sum_{\text{叶子}} L,\qquad
\text{树} = \sum_{\text{节点}} \ell
$$

| 符号 | 是什么 | 从哪来 |
|---|---|---|
| $\ell$ | 一个节点自己存的 token 数，即框里的数字 | 本步 |
| $L$ | 一片叶子的完整 prompt 长度 = 根到它路上的 $\ell$ 之和 | 本步 |

### 代入图上的数

| 叶子 | $L$ |
|---|---|
| q1 | 512 + 300 + 90 = 902 |
| q2 | 512 + 300 + 140 = 952 |
| q3 | 512 + 250 + 60 = 822 |
| q5 | 512 + 250 + 120 = 882 |
| 合计（像第 1 步那样各存一份） | 3,558 |

树里每个节点存一次：512 + 300 + 250 + 90 + 140 + 60 + 120 = 1,472 个 token。

图上底部那行只算了根：4 段对话共用一份 512，而不是 4 × 512 = 2,048。

按第 2 步的引用计数：system prompt 节点的计数是 4（4 个运行中的 request 都经过它），集 A 和集 B 各是 2，每片叶子是 1。

### 接下来

第 5 步来一个新 request，沿树往下匹配。

## 第 5 步 · 新来者沿树匹配

> **一句话：** q4 有 992 个 token，沿树匹配上 system prompt 和集 A 共 812 个，只 prefill 180 个；首 token 4.8 ms 而不是 16 ms，准入只要 2 个 page 而不是 8 个。

### 图上是什么

- 第 4 步的树；根到集 A 的边变成蓝色粗线，根和集 A 的框填浅蓝：匹配上的路径。
- 集 A 下多出一个橙色粗框「q4（新）· 180」，用橙线连上。
- 右侧两行：已匹配 812 / 992 个 token → 只 prefill 180；首 token：4.8 ms 而不是 16 ms。
- 底部一行：准入时需要的 page：尾部 2 个，而非 8 个。
- 灰色脚注：SGLang 按整 page 匹配，page 为 128 个 token 时匹配会停在 768；其默认 page 是 1 个 token，此时 812 精确匹配。

### 公式

$$
t_{\text{step}}(n) = \max\!\left(t_{\text{mem}},\ t_{\text{comp}}(n)\right)
$$

$$
t_{\text{mem}} = \frac{M_W}{BW},\qquad
t_{\text{comp}}(n) = \frac{n\,f}{F}
$$

| 符号 | 是什么 | 大小 | 从哪来 |
|---|---|---|---|
| $n$ | 这一步要 prefill 的 token 数 | | 本步 |
| $m$ | 匹配长度 | | 第 3 步 |
| $M_W$ | 权重字节数 | 16 GB | 第 4 章第 2 步；`W_GB` |
| $BW$ | HBM 带宽 | 3.35 TB/s | `src/numbers.ts` 的 `BW` |
| $f$ | 一个 token 的计算量 | 16 GFLOP | 第 4 章第 5 步；`GFLOP_PER_TOKEN` |
| $F$ | GPU 算力 | 989 TFLOP/s | `TFLOPS` |
| $t_{\text{step}}(n)$ | 一个 $n$ 个 token 的 prefill 步的耗时，读权重和计算取较慢的那个 | | 第 4 章第 5、8 步 |

首 token 要等这次 prefill 跑完，所以首 token 时间 ≈ $t_{\text{step}}(\text{prompt 长度} - m)$。

### 代入图上的数

| 量 | 计算 | 结果 | 图上 |
|---|---|---|---|
| q4 的 prompt | 512 + 300 + 180 | 992 | 992 |
| $m$ | 512 + 300 | 812 | 812 |
| 要 prefill | 992 − 812 | 180 | 180 |
| $t_{\text{mem}}$ | 16 ÷ 3.35 | 4.78 ms | |
| $t_{\text{comp}}(180)$ | 180 × 16 ÷ 989 | 2.91 ms，比读权重短 | |
| $t_{\text{step}}(180)$ | max(4.78, 2.91) | 4.78 ms | 4.8 ms |
| $t_{\text{comp}}(992)$ | 992 × 16 ÷ 989 | 16.05 ms，比读权重长 | |
| $t_{\text{step}}(992)$ | max(4.78, 16.05) | 16.05 ms | 16 ms |
| 准入时新 page | $\lceil 180/128 \rceil$ | 2 | 2 |
| 不匹配时 | $\lceil 992/128 \rceil$ | 8 | 8 |

准入检查（第 7 章第 7 步）只数新要的 page；匹配上的 812 个 token 已经在树里的 page 上。

### 脚注：按整 page 匹配

树里存的是整页。page 大小为 $p$ 时，匹配长度向下取到 $p$ 的整数倍：

| $p$ | 匹配到 | 要 prefill |
|---|---|---|
| 128（图上的画法） | $\lfloor 812/128 \rfloor \times 128 = 6 \times 128 = 768$ | 992 − 768 = 224 |
| 1（SGLang 默认） | 812 | 180 |

### 接下来

第 6 步看收益最大的场景：同一段对话的下一轮。

## 第 6 步 · 对话：每轮只 prefill 新问题

> **一句话：** 第 $i$ 轮的 prompt 是之前全部对话加新问题；没有树三轮共 prefill 2,410 个 token，有树只要 740 个。

### 图上是什么

- 行标题：一段对话，三轮 · 每轮 prefill 要计算什么。
- 每轮一行，从左到右：
  - 浅蓝条「第 1 轮 · 720 个 token · 已缓存」「第 1–2 轮 · 950 个 token · 已缓存」：之前说过的全部；第 1 轮没有这一段。
  - 蓝条：这一轮的问题，第 1 轮是「system + q1 · 600」，之后是 q2 · 80、q3 · 60。
  - 橙条：这一轮的回答，120 和 150；第 3 轮还没回答。
  - 条下一行：无树时 prefill 多少个 token · 有树时多少个。
- 底部两行：三轮合计；回答也会被缓存，只差最后一个 token：它是下一轮的前缀。
- 灰色脚注：每轮还要加一个 token，见下文。

### 公式

$$
c(i) = \sum_{u < i} (q_u + a_u)
$$

$$
\text{无树} = \sum_i \big(c(i) + q_i\big),\qquad
\text{有树} = \sum_i q_i
$$

| 符号 | 是什么 | 从哪来 |
|---|---|---|
| $q_i$ | 第 $i$ 轮新问题的 token 数（第 1 轮含 system prompt） | 本步，蓝条 |
| $a_i$ | 第 $i$ 轮回答的 token 数 | 本步，橙条 |
| $c(i)$ | 第 $i$ 轮之前的全部对话，即浅蓝条 | 本步 |

这里的 $q_i$ 是问题长度，不是第 2 章的 query 向量。第 $i$ 轮的 prompt = $c(i) + q_i$，而 $c(i)$ 就是第 3 步的匹配前缀：前几轮的 token，顺序也一样。

### 代入图上的数

| 轮 | $c(i)$ | $q_i$ | 无树：$c(i) + q_i$ | 有树：$q_i$ |
|---|---|---|---|---|
| 1 | 0 | 600 | 600 | 600 |
| 2 | 600 + 120 = 720 | 80 | 800 | 80 |
| 3 | 720 + 80 + 150 = 950 | 60 | 1,010 | 60 |
| 合计 | | | **2,410** | **740** |

无树的总量随对话变长越来越大，有树只和问题长度有关。

### 回答为什么也在树里

decode 每生成一个回答 token，下一步把它送回模型，这时写下它的 k 和 v（第 3 章第 5 步）。所以回答也进了缓存。

**脚注的那一个 token：** 回答的最后一个 token 被采样出来后，request 就结束了，它从没被送回模型，k 和 v 不存在。下一轮要从它开始补算，所以第 2、3 轮实际 prefill 81 和 61 个 token。

### 接下来

第 7 步：树一直长，内存总会不够，哪些节点先走。

## 第 7 步 · 驱逐：最久未用的先走，运行中的钉住

> **一句话：** q3 和 q5 结束后，集 B 那一支引用计数变 0；池子要 page 时，它是最久未用的一支，被收回；q1、q2 还在跑，它们经过的节点被钉住。

### 图上是什么

动画分三段：

1. 第 4 步的树，根旁边绿字「📌 已钉住」。
2. q3、q5 变灰，右上角绿色 ✓，下面绿字「已完成 · 无人使用」。
3. q3、q5 落下消失；集 B 变成灰色虚线框，上面红色标签「已驱逐」。下面红字：池子需要 page · 集 B 是最久未用的分支 → 其 250 个 token 的 k 和 v 归还池子。

底部一行：节点引用计数为零时，其 page 可回收；运行中的 request 整条路径都被钉住。

### 规则

- request 结束，节点**不删**：之后同样前缀的 request 还能匹配上。
- 第 2 步的引用计数，在树上就是「路径经过这个节点的运行中 request 个数」。request 开始用一条路径时，路上每个节点 +1；结束时 −1。
- 计数 > 0 的节点被**钉住**：这些 request 每个 decode 步都要读这些 page，不能收回。
- 池子要 page 时，从计数为 0 的**叶子**里挑最久没被用过的先收回（LRU，least recently used）。一个父节点的孩子都没了、自己计数也是 0，它就成了新的叶子，排进候选。

### 代入图上的数

| 节点 | 结束前计数 | 结束后计数 |
|---|---|---|
| system prompt | 4 | 2（q1、q2）→ 钉住 |
| 集 A | 2 | 2 → 钉住 |
| 集 B | 2 | 0 |
| q3、q5 | 1 | 0 |

收回的内存：

| 节点 | token | 字节（× 128 KB） |
|---|---|---|
| 集 B | 250 | 31.25 MB |
| q3 + q5 | 60 + 120 = 180 | 22.5 MB |
| 合计 | 430 | 53.75 MB |

图上的红字只算了集 B 的 250 个；q3、q5 的 180 个也一起回到池里。

### SGLang 里

- `RadixCache` 的节点有 `lock_ref`，就是这里的引用计数；`inc_lock_ref` / `dec_lock_ref` 沿路径到根逐个加减。
- `evict` 只从计数为 0 的叶子里挑，按 `--radix-eviction-policy` 排序，默认 `lru`。所以实际顺序是先收 q3、q5 两片叶子，集 B 变成叶子后再收它。

### 驱逐不影响正确性

被驱逐的只是缓存。之后来一个同样 prompt 的 request，第 5 步的 $m$ 变小，多 prefill 一些，结果不变。

### 接下来

第 8 步：scheduler 能不能利用「谁匹配得多」来排顺序。

## 第 8 步 · scheduler 按匹配长度排队

> **一句话：** 同样三个等待的 request，先来先服务按到达顺序 X、Y、Z；最长前缀匹配按 $m$ 从大到小排成 X、Z、Y。SGLang 默认前者。

### 图上是什么

- 行标题：同样三个等待的 request · 下一个 prefill batch 给谁？
- 上面灰框「先来先服务 · SGLang 默认」，下面蓝框「最长前缀匹配 · 可选启用」。框左边一根向下的箭头「时间」：越靠上越先跑。
- 每个 request 一根条：浅蓝是已在树中的部分（$m$），深蓝是必须 prefill 的部分；右边写「prefill 多少 / 共多少个 · 耗时」。
- 底部图例：浅蓝 = 已在树中，深蓝 = 必须 prefill。
- 灰色脚注：SGLang: `--schedule-policy lpm`（默认 `fcfs`）· 等待的 request 超过 128 个时，lpm 退回 fcfs。

### 代入图上的数

每个的耗时是第 5 步的 $t_{\text{step}}(n - m)$，$n$ 是 prompt 长度：

| request | $n$ | $m$ | $n - m$ | $t_{\text{comp}}$ | $t_{\text{step}}$ | 图上 |
|---|---|---|---|---|---|---|
| req X | 992 | 812 | 180 | 2.91 ms | max(4.78, 2.91) = 4.78 ms | 4.8 ms |
| req Y | 700 | 0 | 700 | 11.32 ms | 11.32 ms | 11 ms |
| req Z | 900 | 512 | 388 | 6.28 ms | 6.28 ms | 6.3 ms |

- req X 就是第 5 步的 q4：匹配 system prompt + 集 A。
- req Z 只匹配 512 个 token 的 system prompt。
- req Y 什么都没匹配上。

### 两种顺序

| 策略 | 怎么排 | 图上的顺序 |
|---|---|---|
| 先来先服务（fcfs） | 到达顺序 | X、Y、Z |
| 最长前缀匹配（lpm） | 按 $m$ 从大到小 | X（812）、Z（512）、Y（0） |

- 两种顺序下 prefill 的总量相同：180 + 700 + 388 = 1,268 个 token。
- 顺序影响的是：一个等待中的 request 的前缀，可能在它被接纳之前就被第 7 步的驱逐收走。lpm 让匹配多的先跑，趁它的前缀还在树里。
- 无论哪种策略，一个 request 被接纳时都会做前缀匹配，复用照样发生；lpm 只改顺序。

### SGLang 里

- `--schedule-policy` 默认 `fcfs`。
- 选 `lpm` 时，等待的 request 超过 128 个（`WAITING_QUEUE_PREFIX_MATCH_MAX`）就临时退回 fcfs：每一步把每个等待的 request 和树匹配一遍、再排序，要花 CPU 时间。
